# API reference

The REST endpoints and WebSocket messages, grouped by area. Swagger UI (`http://localhost:8413/openapi`) is the generated list; this is the one that says what each is for and what it refuses.

## API Endpoints

- **REST API**: `http://localhost:8413/api/rest`
- **WebSocket**: `ws://localhost:8413/api`
- **Swagger UI**: `http://localhost:8413/openapi`

### FX REST Endpoints
- `GET/POST /api/rest/projects/{id}/speed-masters` + `GET/PUT/DELETE .../{mid}` - Speed-master CRUD, and the only REST tempo surface: `PUT` with `bpm` sets the stored default *and* retunes the live clock when the project is current (delete guards: `SPEED_MASTER_PROTECTED` for master 1, `SPEED_MASTER_IN_USE` when referenced). Tap is WS-only (`speedMasters.tap`)
- `GET /api/rest/fx/active` - List active FX
- `POST /api/rest/fx/add` - Add an FX to a fixture (`fixtureKey`), or one FX over `targets` — fixtures and groups in order, a selection (effects plan D3), every item checked at once
- `DELETE /api/rest/fx/{id}` - Remove an FX
- `POST /api/rest/fx/{id}/pause` / `resume` - Control an FX
- `PUT /api/rest/fx/{id}` - Edit a running FX in place (id and phase kept); one parse with the `updateFx` frame (`applyFxUpdate`), 400 `FX_UPDATE_REFUSED` / 404 `FX_NOT_FOUND`. `amount` (0–1), `direction` (`FORWARD | BACKWARD | BOUNCE`) and `runs` (≥ 1; `runForever: true` clears it) are dynamics fields, edited with the phase kept (effects plan session 1), and the add routes take all three. `spread` (0–2), `wings`, `segments` (≥ 1) and `parts` (≥ 0, 0 off) are the spread's shape (effects plan session 2), dynamics fields too, the add routes taking them as well, with `spreadUnit` (`CYCLE | STEP`, fx-settings plan D6: under `STEP` `spread` is 0–16 of the FX's own steps; a swap onto an FX with no steps leaves it for the `CYCLE` spread that keeps the heads' offsets); wings above 1 under a mirrored Order — the request's or the FX's — is refused. `ownBpm` moves a beat FX onto its Own tempo (fx-speed plan D3), or sets a new tempo with the phase kept; naming a master takes it off; `natural: true` is how a wall-clock FX goes back to unscaled (D4); either beside a master is refused; a move between Own tempo and a master restarts the FX's phase, since it changes the loop. The old `seconds` still reads (D5). `POST /fx/add`, `POST /groups/{name}/fx` and `POST /programmer/fx` take `ownBpm` and `natural` too, and default an omitted `cycle` to one bar. `targets` (apply-model plan session 2) says which heads the edit is for: absent or every head the FX paints is the in-place edit; some of them **splits** them off — the FX becomes one instance per head, each carrying its member's offset, set amount and context so nothing jumps, the named heads' copies taking the edit — answered `{splitFxId, edited, rest}`. 409 `FX_SPLIT_LAYER_FX` for a programmer layer's FX, `FX_SPLIT_NOT_LOCAL` for a cue's or a manual one; a shape change (Order, Spread, Wings, Segments, Parts, element mode or filter) with some heads is 400 `FX_UPDATE_REFUSED`. See `docs/fx-engineering.md` §"Local FX follow the selection"
- `POST /api/rest/projects/{id}/programmer/fx` - The bare FX press (apply-model plan §3.4, D5): `{fxType, attribute, targets, families?, parameters?}` plus every FX field `POST /fx/add` takes, as **one Local FX** over the selection (one group FX on a group); no `cycle` is one bar and no master the one whose `family` is the FX's library `family` (D16, as MCP and the picker stamp). Its family is the group of the attribute it drives, as Record reads it (a Pulse on `uv` is Colour). It first takes the selected heads off every other Local FX of that family — stopping one wholly inside, narrowing one partly inside into one instance per head it keeps — unless `stack: true` (FX editor plan D6, §3.6), which adds it on top and stops and narrows nothing, an absent blend or `amount` starting on its family's row of `fx/FxStacking.kt` (Intensity `MULTIPLY` at 100 %, Position `ADDITIVE` at 100 % with both centres at 128 — `OVERRIDE` at 100 % for one with no centres — Colour and Beam `OVERRIDE` at 50 %). 400 `FX_OUTSIDE_MASK` / `FX_NEEDS_SELECTION`; answers `{fxId, stopped, narrowed}`. Every Local FX applies above every programmer layer's FX (`BASE + LOCAL_OFFSET + localRank`, a new one on top of its lane, FX editor plan D5) and the `programmer.moveFx` frame re-ranks one; see `docs/fx-engineering.md` §"Programmer suppression and the priority band". Current project only
- `POST /api/rest/projects/{id}/fx/preview` - What the selection's heads will hold over a window (FX editor plan §3.3, D7): `{targets, fx: [{fxId} | {draft} | {fxId, draft}], include: STACK | ONLY, window: {cycles? | beats? | seconds?}, solo?, notional?}`, a draft built by `/fx/add`'s write boundary and never added, a draft move run through `PUT /fx/{id}`'s parse on a copy, `notional: n` the drafts on *n* heads the rig lacks (FX editor plan D15, `fx/NotionalRig.kt`: no `targets`, drafts only, `include: ONLY`), answered from `fx/FxSampler.kt` — rows in the first FX's Order, lanes by family with underneath, result and each FX's output, per FX its offsets, starts, holding ranges and offset ladder, the clock, `truncated` — and nothing written. 400 `FX_PREVIEW_INVALID` names every problem; current project only, both roles. See `docs/fx-engineering.md` §"Previewing an FX"
- `POST /api/rest/fx/{id}/reset` - Re-apply a programmer palette layer's **current** FX to the instance it spawned, id and phase kept, and re-key it so the next recook keeps it (fixture-fx-sheets plan W5); 409 `FX_NOT_FROM_PALETTE` / `FX_PALETTE_GONE`. See `docs/fx-engineering.md` §"Programmer suppression and the priority band"
- `GET /api/rest/fx/library` - Available FX types

### Venue Endpoints
All four are **admin only** (mounted in `adminOnly`; venue plan §3.5, D3), REST only — no WS operation:
- `GET /api/rest/venues/{id}/versions` - History: every version newest first (`number`, `note`, `publishedAt`, `publishedBy`, `snapshotProjectId`), `installed`, and the draft's `{changes, outputChanges}` against it
- `GET /api/rest/venues/{id}/versions/{from}/diff/{to}` - What changed, `{output: [...], drawing: [...]}`; each side a version number, `0` the empty venue before v1, or `draft`. 404 `VENUE_VERSION_UNKNOWN`, 400 `VENUE_VERSION_INVALID`
- `POST /api/rest/venues/{id}/publish` `{note}` - Freeze the draft as the next version; 400 `VENUE_NOTE_REQUIRED` / `VENUE_NOTE_TOO_LONG` (500 characters), 409 `VENUE_DRAFT_EMPTY`. With a repo attached it publishes through it (session 4, P7): pulls first, 409 `VENUE_VERSION_TAKEN` when the remote already has the number (or refuses the push), else commits `vN: note`, tags and pushes, then makes the version here from the tagged tree; 409 `VENUE_PUBLISH_PULL_ONLY` on a `sync.push = false` desk. Fires `projectDetailsChanged`
- `DELETE /api/rest/venues/{id}/draft` - Discard the draft: the venue's rows become the installed version's again, uuids and all (name and description stay); 409 `VENUE_NOTHING_PUBLISHED`. A live venue reloads
- A show's id on any of them is 409 `NOT_A_VENUE`. *Add venue* is `POST /projects` `{kind: "VENUE"}` (admin); `ProjectDto` carries `kind`, and `FixturePatchDto` its `uuid`. Deleting a venue deletes its versions — refused 409 `VENUE_IN_USE` while a show pins it. History also answers `shows` (every show on the venue, with its version)

### Show-on-a-venue Endpoints
Venue plan sessions 3–7; REST only, no WS operation (`venue.hold` is outbound only):
- `POST /api/rest/projects/{id}/venue/extract` `{name, include?, dryRun?}` - **Admin only**: move a show's universes, patches, riggings, regions, VENUE-layer elements, seating (Fixed moves, Preset is copied), groups, camera views and parked channels into a new venue, publish v1 and pin the show — one transaction, uuids kept, links re-pointed through `VenueLinks`, the moved records' machine overrides and scene images following them. `dryRun` answers the same run rolled back. 400 `VENUE_EXTRACT_INCOMPLETE` (a part that would point out of the venue), 409 `VENUE_EXTRACT_REFUSED` / `_EMPTY`. A live show reloads
- `POST /api/rest/projects` `{…, venueId, seatingPresetUuid?}` - A new show on that venue, pinned to its installed version (409 `VENUE_NOTHING_PUBLISHED` before v1), with a copy of that version's Preset seating block as its own stalls when named (400 `SEATING_PRESET_UNKNOWN`, session 7); `ProjectDto.venue` is `{uuid, id, name, version, installed, behind, drawingChanges}`, `behind` `NONE | DRAWING | OUTPUT` (session 6). The list's venue rows carry `venueSummary` `{version, publishedAt, patches, universes, riggings, fixedSeating, shows, behind}` — the Projects page's venue card. Every list row also carries `parks` (its effective parked channels) and `safeBlackout` (*Make rig safe*'s blackout holds on it; runtime only), which the switch confirmation reads (navigation plan §4.3)
- `POST /api/rest/projects/{id}/detach` `{dryRun?}` - *Detach* (session 7, D9): the effective rig at the pin written into the show's own rows, uuids kept, links re-pointed, the venue's machine overrides copied, hides, overrides and pin cleared — one transaction, `dryRun` the same run rolled back. A behind show detaches at its pin (the answer's `behind`, `installed`). The answer's `detachedFrom` `{venueUuid, version, venueId?, venueName?}` is the origin it records, which `ProjectListDto` and `ProjectDetailDto` carry too (venue-attach plan D1). 409 `NOT_A_VENUE_SHOW` / `VENUE_MISSING` / `VENUE_DETACH_BLOCKED`. Both roles; a live show reloads, which lifts its hold
- `GET /api/rest/projects/{id}/venue/attach?venue=&to=` + `POST …/venue/attach` `{venueId, to?, decisions, dryRun?}` - *Attach to venue…* (venue-attach plan session 2): the review — `AttachReviewDto`, the pairing's `output`, `drawing`, `inherited` counts, `overrides`, `kept`, `hides`, `additions`, `incoming`, `renames` (each with its reach, `usedBy`), `decisions` (`identity:` / `hall:` / `group:` / `drift:` `KEEP_MINE | TAKE_VENUES`, without an origin `hide:` `TAKE_VENUES | HIDE_VENUES`, each with a default), `overlaps` (P8, `KEEP_BOTH | READDRESS_MINE | HIDE_VENUES | REMOVE_MINE`, which must be answered), `blockers`, `deadReferences`, `behind`, `runAgainst` and `notes` (a live show's renamed fixtures, whose programmer values the reload drops) — is the attach rolled back; the `POST` writes it in one transaction. 409 `NOT_A_STANDALONE_SHOW` / `VENUE_NOTHING_PUBLISHED` / `ATTACH_UNDECIDED` / `ATTACH_BLOCKED`, 404 `VENUE_VERSION_UNKNOWN`, 400 `ATTACH_INVALID`. Both roles; a live show reloads, and runs against its pin when attached behind on output. MCP's `attach_to_venue` is the same call
- `GET /api/rest/projects/{id}/seating/presets` + `POST …/seating/from-preset` `{elementUuid, force?}` - A venue's Preset seating at its installed version, or a show's at its pinned one, and the show's own seating; *Replace from preset* swaps every seating block the show owns for a fresh copy, moving its seat views to it (409 `STAGE_ELEMENT_IN_USE` naming one the copy has no seat for, `force` leaves it without one) and the stalls' scenery with it. 409 `NOT_A_VENUE` / `SEATING_PRESET_NAME_TAKEN`, 400 `SEATING_PRESET_UNKNOWN`. Both roles (session 7)
- `GET /api/rest/projects/{id}/venue/update?to=n` + `POST …/venue/update` `{to?, decisions, dryRun?}` - *Update* (session 6, `venue/VenueUpdate.kt`): the review — the hall's changes `{output, drawing}` beside `carryOver`, `drift` (an override the target moved under, kept unless answered `TAKE_VENUES`), `dropped` (hides, overrides, recolours, orders and links whose record the target lacks), `orders` (a venue group the venue reordered under the show's order of it: `order:<groupUuid>` `KEEP_MINE | TAKE_VENUES`, kept unless answered), `decisions` (an address overlap the update introduces: `KEEP_BOTH | READDRESS_MINE | HIDE_VENUES | REMOVE_MINE`, P8), `blockers` (a key or name clash with the show's own, a show patch on a removed universe) and `deadReferences` (every key the update removes that the show still names — cue rows, layers and FX, Looks, palettes, bindings and scripts) — is the update rolled back; the `POST` moves the pin and re-points every `VenueLinks` link in one transaction. 409 `VENUE_UPDATE_UNDECIDED` / `VENUE_UPDATE_BLOCKED` / `VENUE_UP_TO_DATE`, 400 `VENUE_UPDATE_INVALID`. Both roles; a live show reloads, which lifts its hold
- `POST /api/rest/projects/{id}/venue/run-against` `{on}` - Lift the hold for this session, or put it back (current project only, both roles; 409 `VENUE_NOT_BEHIND`); answers the hold. Runtime only: kept by a reload at the same pin and installed version, dropped by another project, a moved pin, a newer version or a restart
- Sync, export, import and clone take a show on a venue (session 4): `POST /projects/{id}/export` writes its own rows, hides and pin; `POST /projects/import`, `POST /cloud-sync/import` and `POST /projects/{id}/clone` answer 409 `VENUE_MISSING` (`{error, code}`) for a show whose pinned version is not on the desk, and so does `POST /projects/{id}/set-current` for one already here; `POST /projects/{id}/sync/run` refuses a pull that would pin one (`VENUE_MISSING`, before the working tree moves). A clone keeps the pin
- `colour` on the patch `PUT`, its bulk path (`PUT .../patches/placements`) and the group `PUT` — one of ten keys, 400 `COLOUR_UNKNOWN` otherwise, every bad entry at once (`models/fixtureColours.kt`). Through a show onto a venue's patch or group, a body naming only `colour` writes the show's recolour (`show_colours`) rather than 409 `VENUE_OWNED`, and `null` takes the venue's back; `FixturePatchDto` and `PatchGroupDto` carry `colour` and, on a venue record, `colourOwner` (`SHOW | VENUE`); `GroupSummaryDto` carries `colour`. See `docs/fixtures-engineering.md` §"Fixture colours"
- `PUT /api/rest/projects/{id}/patches/{pid}/hidden` `{hidden}` + `GET .../patches/hidden` - Hide a venue patch in a show, or bring it back; the hidden ones as Patch list rows. `GET /projects/{id}/hides` and `PUT .../hides/{KIND}/{uuid}` `{hidden}` do it for all six kinds (`PATCH | RIGGING | ELEMENT | REGION | GROUP | VIEWPOINT`). 409 `NOT_A_VENUE_RECORD`, `VENUE_HIDE_IN_USE` (something in the show still uses it), `KEY_TAKEN_BY_SHOW`. `FixturePatchDto`, `PatchGroupDto` and `UniverseConfigDto` carry `owner` (`SHOW | VENUE`)
- `PUT /api/rest/projects/{id}/patches/{pid}/facets/{facet}` `{value | null}` - Make one facet of a venue patch this show's own (session 5) — `ADDRESS | POSITION | FOCUS | MEDIA | NAME`, the whole facet (placements named by the venue placement's uuid), recording the pinned version's value as `base` when new — or take the venue's back with `null` (also *Take venue's*). Checked like the patch write it stands for, every problem at once: 400 `FACET_INVALID` / `FACET_UNKNOWN`; an address overlap is allowed and answered in `warnings` (P8). 409 `NOT_A_VENUE_RECORD` (a show's own patch, a standalone show, a venue), `FACET_PATCH_HIDDEN`; a version is `VENUE_VERSION_READ_ONLY`. A stored show write an operator may make. `POST .../facets/{facet}/keep-mine` is *Keep mine*: base := the venue's current value (409 `FACET_NOT_OVERRIDDEN`). Both answer `{patch, changed, warnings}`; `FixturePatchDto.facets` lists a venue patch's overridden facets `{facet, value, venue, drifted, base?, dormant}`, its fields already the overridden ones, and `universeConfigUuid` (also on `UniverseConfigDto`, as `uuid`). `NAME` is `{displayName}`, not blank, read by every reader of the patch's name in the show (`RigScope.nameOf`); it, Address and Media reload the live rig. The patch PUT on a venue patch stays `VENUE_OWNED`, naming this route; the Stage editor's drag of one is not turned into a Position override

### Prompt Book Endpoints
- `GET /api/rest/projects/{id}/prompt-book/text` - The book's script as the desk read it (prompt-book navigation plan D1): `{state: "READY", scriptHash, index}` with an ETag on the hash, 202 `BUILDING` while PDFBox reads it in the background (asking starts it), `SCRIPT_MISSING` when the PDF is not on this desk, `UNREADABLE`; 404 with no book. Any project, both roles. The index is `<appDataDir>/prompt-scripts/{projectUuid}/{hash}.text.json`, a cache: no table, never synced or backed up. See `docs/prompt-book-engineering.md`

### Remote Access Endpoints
- `GET /api/rest/install/cloud`, `POST/DELETE .../install/cloud/adoption`, `DELETE .../install/cloud[?force=true]` - This desk's adoption by Lighting7 Cloud (cloud-p0 plan D14), admin only, machine-local; every answer is the state `cloud.state` streams. Adopting is refused 403 `CLOUD_ADOPT_LOCAL_ONLY` on the public listener and 409 `CLOUD_NEEDS_ACCOUNT` on a desk with no accounts (D5); unadopt is 409 `CLOUD_UNREACHABLE` when the cloud cannot be told, unless `force`. `GET/PUT .../install/cloud/remote` `{remoteAccess?, mcpAccess?, approveSessions?, allowScripts?, allowEffects?, allowCommands?}` are what may come through the cloud (cloud-p1 plan D6, D13), off at adoption, and what any remote caller may do, the Cloud tab's *Remote access*; the `PUT` is 403 `CLOUD_SETTINGS_LOCAL_ONLY` on the public listener and 409 `CLOUD_NOT_ADOPTED` for a cloud switch before adoption. `GET .../install/cloud/heartbeat` is the last heartbeat built for the cloud, as JSON (cloud-p3 plan D2). `GET .../install/cloud/sessions` lists the open and recent remote sessions and `DELETE .../sessions/{sid}` ends one, from either listener; with *Approve each new session* on, an offer waits up to 60 s for `POST .../sessions/{sid}/allow` or `…/deny`, refused on the public listener (403 `CLOUD_APPROVAL_LOCAL_ONLY`), else `REMOTE_SESSION_DENIED`; an *Allow* is 409 `CLOUD_SESSION_LINK_CHANGED` when the account's link moved while it waited, which shows it afresh. `cloud.state` carries the three cloud switches as `remoteSwitches`. See `docs/cloud-engineering.md`
- `GET/PUT /api/rest/install/cloud/backups` `{enabled?, dailyAt?, nightly?, onQuit?}` + `POST .../backups/run` - Off-site backups (cloud-p3 plan D5–D8), admin only, machine-local (`backup_settings`): the switch, its two schedules — each night at a time, and on *Quit desk*, which then backs up before it exits, for at most 15 minutes (`QUIT`; a quit's backup left staged is finished at the next start) — a run in progress, the last result. The `PUT` is 403 `CLOUD_SETTINGS_LOCAL_ONLY` on the public listener and 400 `BACKUP_SETTINGS_INVALID` for a time not `HH:mm`; `run` is *Back up now*, 202, 409 `CLOUD_NOT_ADOPTED` before adoption, and on the public listener 403 `BACKUP_REMOTE_OFF` while the switch is off. A backup is `backup/InstallBackup.kt`'s archive — a `VACUUM INTO` snapshot on its own connection, `prompt-scripts/`, `scene-images/`, `sync/` and `local.conf` — sealed by `BackupCipher` under the org's data key as it is written, and uploaded in 64 MiB parts with a resume, all on `backup-1`; the cloud's `backup.request` runs one only with the switch on (`backup.off`). See `docs/cloud-engineering.md` §"Backups"
- `GET/DELETE /api/rest/install/cloud/restore` + `POST .../restore/confirm` `{name}` - Restoring onto this desk (cloud-p3 plan D9, D10), admin only: what the adoption's approval asked for (`restore {replacesInstallId?, replacesName?, backupId?}`, kept on `cloud_connection` until answered), the backup, the name to type and a confirm's phase; the confirm is the desk's own listener's alone (403 `CLOUD_RESTORE_LOCAL_ONLY`), 400 `CLOUD_RESTORE_NAME_MISMATCH` without the old install's name, and answers 202 while `backup/RestoreService.kt` downloads, decrypts and checks the backup (`BACKUP_CORRUPT`, `BACKUP_TOO_NEW`) before anything changes, then confirms the replacement (the desk reconnects as the old install id) and stages the backup; `DELETE` declines it, a staged backup too until the restart. The staged backup applies at the next start, in `State.initDatabase` before the pool opens (`backup/RestoreApply.kt`): the database and trees swapped, the migrations run, this machine's `installs` and `cloud_connection` rows written back, sessions emptied, any failure undone. `cloud.state`'s `restartToRestore` asks for the restart. See `docs/cloud-engineering.md` §"Restore"
- `POST /api/rest/cloud/session/token` + `DELETE /api/rest/cloud/session` - A remote session's own refresh (the new token as the bearer, which must expire later or the session ends) and end, open to an unlinked session (cloud-p1 plan D4, D5). On the public listener a request with `Authorization: Bearer` and the sidecar's `Lighting7-Link` secret is judged as a remote session through the cloud (`cloud/RemoteSessions.kt`) by `resolveCaller`, the gate's, the WS upgrade's and `auth/status`'s one answer to who is calling; `auth/status` answers an unlinked one `{unlinked, email}`. See `docs/cloud-engineering.md` §"Remote sessions"
- `POST /api/rest/users/{id}/cloud-invite` `{email}` + `DELETE .../cloud-invite`, `DELETE /api/rest/users/{id}/cloud-link`, `GET/DELETE /api/rest/cloud/link`, `POST /api/rest/cloud/link/prove` `{username, password}` - Links between cloud accounts and desk users (cloud-p1 plan D12, `cloud/CloudLinks.kt`): an admin's invite (sent as `link.invite`, mailed only once an owner or admin of the org approves it in the portal; 409 `CLOUD_OFFLINE` / `CLOUD_INVITE_PENDING` / `CLOUD_LINK_EXISTS`) and its cancel, an admin's unlink, the caller's own link and unlink, and an unlinked remote session's prove-once, under the public listener's lockout, after which that session is the user. Every unlink ends the account's remote sessions and tells the cloud `link.removed`; `UserDto` carries `cloudLink` and `cloudInvite`; each change is a `cloud_link_events` row. See `docs/cloud-engineering.md` §"Links"
- `GET/PUT /api/rest/install/telemetry` - The install's Sentry switch, machine-local. `GET` is open to any caller, signed out included, on both listeners, answering `{enabled, release, environment, tracesSampleRate, browserDsn, replaysSessionSampleRate, replaysOnErrorSampleRate}`; `PUT {enabled}` is admin only and starts or stops Sentry live, the browsers' with it. `sentry.enabled = false` in local.conf wins. See `docs/observability-engineering.md`
- `POST /api/rest/install/onboarding/finish` `{openProjectId?}` - Admin only. A new desk's onboarding (`routes/installOnboarding.kt`): `installs.onboarding_pending` is set when the first admin is created and `GET /install` answers it as `onboardingPending`; finishing clears it, and with `openProjectId` switches to that project and deletes the project it left if that one is an empty standalone show with no repo (its export holds nothing but the default speed masters) — the `Default` the desk booted on. 409 `ONBOARDING_DONE`. The repo listing's `projectKind` is what lets onboarding import venues before their shows
- `POST /api/rest/install/quit` `{force?, skipBackup?}` - *Quit desk* (venue-visit plan S6, D13): admin only and **never remote** — 403 `QUIT_LOCAL_ONLY` on the public listener whatever the role; 409 `RIG_NOT_SAFE` unless *Ready to switch off* holds, the rig is made safe and its lamps only cooling, or `force`. Answers 202, backs up first when the desk backs up on quit, for at most 15 minutes (`backingUp`, the backups' status; `skipBackup` ends the wait), flushes the scaler writer and exits 0; the Windows launcher exits with it
- `POST /api/sentry` - The browser SDK's envelope tunnel, open to every caller on both listeners and outside the warm-up and auth gates: spooled to `<appDataDir>/sentry-browser/` only while telemetry is on, at most 1 MB, and only if its header names `sentry.browserDsn`; forwarded byte for byte by a worker only `module()` starts, and deleted when telemetry is turned off. See `docs/observability-engineering.md` §"The tunnel"

### Control Surface Endpoints
- `GET /api/rest/surface-functions` - The function catalogue (surface-setup plan D15): every function an editor offers, from the desk's specs — its id, label, group, the inputs, subjects and Hows it takes, its parameters with their options, where it writes and a line of help; two entries for a grand master and a tempo, whose level or BPM makes a button of each. Static per build (`midi/SurfaceCatalogue.kt`)
- `PUT /api/rest/projects/{id}/surface-bindings/slot` `{deviceTypeKey, controlId, part, layer, binding, takeoverPolicy?}` + `DELETE …/slot` `{deviceTypeKey, controlId, part, layer}` - The editors' one write: whatever the slot holds becomes the binding (the row rewritten in place), refused by the function's spec with the codes the other writes answer; the delete is 404 on an empty slot. `layer` null is both. `GET …/slot/preview?deviceTypeKey=&controlId=&part=&layer=` answers `{place, replaces}`: where the slot is in words and what a write there would change (the binding it replaces, a layer's own that keeps beating it, a both-layers binding it beats on one, a job it takes the control from), the desk's words for *Assign to surface…* (`SurfaceUses.slotPreview`). `GET/POST/PATCH/DELETE …/surface-bindings[/{bid}]` stay, binding only — the old union's `target` is no longer a write and no row answers it. See `docs/midi-control-surface-engineering.md` §"The served picture"
- `GET /api/rest/surface-job-kinds` + `GET /api/rest/projects/{id}/surface-jobs` + `GET/PUT/DELETE …/surface-jobs/{deviceTypeKey}/{region}?layer=` - Jobs (surface-setup plan D11): the kinds of job a region can hold, each with the items it takes and the catalogue entries a function item may be; a project's jobs; and one region's job on one layer (`layer` absent for both), the `PUT` `{kind, items}` the whole job, refused 400 by the code the binding writes answer or `SURFACE_JOB_INVALID` (a kind that does not fit the region, more items than slots, an item of the wrong sort). A region's job derives a binding for every control in it that has none of its own, live jobs following the selection or the showing busk page. `ControlSurfaceTypeDto.jobRegions` lists a profile's regions, their slots and the kinds that fit.
