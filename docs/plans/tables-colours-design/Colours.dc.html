Both reads fastest. The wash gives a block of red rows at a glance, as a ChamSys head window does, and the swatch keeps the colour readable on a selected row, where the selection wash sits over the tint. The left edge is not used, because selection and a cue's own row already draw there. The Tweaks panel switches the mark for the whole board.

Identity, never state. A colour marks which fixture: the name cell, a tile's top band, a stage label, a DMX footprint, a surface's scribble strip. It never fills a value cell or draws a ring, because those say who owns the value, and a red name must not look like a red value.

Names, not hex. The stored value is the key (red, lime, …). Each key has a dark and a light value in index.css (--tag-red, …), so the theme toggle works and colour:red means one thing in a filter, in ⌘K and to Claude.

Cyan is the close one. It sits between teal and sky in hue, but it is lighter than both and only ever marks a name, so it stays. If it reads as a cue in practice, it is the one to swap for magenta.

One column, every kit gesture. Marquee down Colour, then Set, a double click, or keys 1–9 and 0 for the ten colours (⌫ clears). It writes through the patch route's bulk path, like Address and Gel, in a single request for the whole marquee.

Colour from group copies the group's colour onto each selected member that has none, or onto all of them with ⌥. It is the explicit form of the inheritance the spec declines.

Venue fixtures (Source: Venue) open the same popover. On a show, the choice is written as the show's recolour, the cell shows yours beside it, and Take venue's clears it, exactly like a facet chip but with no drift to answer.

D · Where it lives, and what it costs

LayerWhat changes
Schemafixture_patches.colour and fixture_groups.colour, both a nullable varchar(16) holding a key, like the prompt-book annotation's colour. They are additive and need no migration. A key the desk does not know reads as none.
Synccolour on FixturePatchJson and FixtureGroupJson. formatVersion 36: an older reader would import the record without the colour and write it back, which is the degraded-record case the bump rule exists for. RichProjectFixture sets a non-default colour on both.
VenueA venue's patches and groups carry their own colour, published with the version. VenueDiff classes it as drawing only, so a show is never held for it. A show recolours through show_colours (project, record_uuid, colour), synced as showColours/, laid over the version by RigScope.effective beside the facets. This works for groups too, which facets do not cover.
REST · WS · MCPcolour on FixturePatchDto, PatchGroupDto and the live GroupSummary. It is written through the patch PUT / bulk route and the group PUT. There is no new frame, because the existing list-changed invalidations carry it. patch_fixtures and edit_groups take colour, and describe_rig lists it, so Claude can say "the red fixtures".
Render costResolved into the row model once, then drawn as --tag on the row and color-mix(in oklch, var(--tag) 16%, var(--background)) on the sticky name cell, which has to stay opaque. A colour edit re-renders only the rows whose key changed. The 3D bodies gain one per-instance colour, written on change. Nothing reads a tag at frame rate.
