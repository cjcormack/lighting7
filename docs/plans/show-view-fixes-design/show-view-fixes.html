Show view editing fixes

Seven changes to how a show is edited on the Show view, the Prompt Book and the Cues table: what Duplicate carries, a bottom editor that stays put, cue numbers as cells, arming from the pip, a per-show switch that says whether the show needs a lock at all, and dragging a selection of cues as one.

1Duplicate carries the follow

Now

Follow (autoAdvance, autoAdvanceDelay) belongs to the stack entry, not the cue, because a shared cue can follow in one stack and not another. POST /cues/{id}/duplicate takes only {stackId}, so it cannot know which place was duplicated, and placeCueInStack creates the copy's entry with follow off.

routes/projectCues.kt:411 · DuplicateCueRequest(stackId) · projectCuesHelpers.kt:1023
Change

The request gains entryId, the place the operator duplicated from. The desk checks that the entry places this cue in this project (400 otherwise) and passes its follow and delay to placeCueInStack, which already takes both. CueActions sends row.entryId; the Cues table sends it only when the cue has exactly one place, as it does for the stack today. Without it (a loose cue, an older client) the copy has no follow, as now.

DuplicateCueRequest(stackId?, entryId?) · CueActions.duplicate

2–3The editor pane is switched on, not summoned

Now

The pane is derived from the selection: paneRow = selectedRows.length === 1 && isCueRow(…). A marquee started on one row opens it, the second row closes it, the sheet gets taller, the rows move under the pointer and the marquee lands on a different row, which can make it one row again. Near the bottom of the list this repeats every few pixels. The Timeline has the same rule for one selected cell.

CueSheet.tsx:647 · StackTimeline.tsx:673 · CueEditorPane.tsx
Change

An Editor toggle in the stack header, drawn on the Table and the Timeline, kept per window in sessionStorage cueSheet.paneOpen beside the pane's height. On, the pane is always drawn at its height whatever is selected, so selecting never changes the layout. Off, it is never drawn. The selection only chooses what the pane shows.

4Cue numbers are cells

Now

The number lives in the sheet's sticky first column with the pip, as a TextCell opened by a double click on one row. The first column is the row selector, so a click there selects the row, a marquee from it selects rows, and the number can never be part of a cell selection. Several cues are renumbered only through the bar's Renumber… over a row selection.

CueSheet.tsx:868–950 · RenumberCuesButton.tsx · SheetTable firstColumn
Change

The first column becomes the row head: the drag grip, the pip and the played tick. The number moves to a Cue # column directly after it, a normal kit cell of its own kind (cueNumber), so it selects with a click, a marquee or the arrow keys like Fade or Notes, and nothing typed into another column reaches it.

5The pip arms the next GO

Now

Arming is a locked gesture only: a locked click on a card's body or the sheet's Cue column calls onSetStandby, and the bar's Arm as next is drawn only while locked. Unlocked, those clicks expand the card or select the row, so a fix-it session mid-show has to re-lock to arm a cue. On a card the pip also sits under the drag grip, which replaces it on hover while unlocked.

CueCardEditor.tsx:154, 199 · CueSheet.tsx:690, 751 · CueRowParts.tsx:43
Change

CueStatePip takes an optional onArm and draws as a button when given: a click arms that cue as the next GO, in every view and in both lock states, and stops there, so it never also selects the row or expands the card. The bar's Arm as next is drawn unlocked too. Every other click keeps its meaning.

CueStatePip({onArm}) · same onSetStandby the locked click uses
  • When the pip is a button: exactly when the locked click arms today, that is when the view is given onSetStandby and the row is not the live one. The live pip and the already-next pip stay read-outs, titled On stage and Next GO. The existing rule that arming is inert off the playhead's stack is unchanged.
  • Cards: the grip moves out of the pip's cell into its own 14 px slot before it, drawn only unlocked, so the pip is always visible and clickable. The card's grid templates gain that track.
  • Table and Timeline: the kit's row grip is already its own element in the row head; the pip only needs the handler and stopPropagation.
  • Keyboard: the pip is a focusable button with the same label as its tooltip, so it is reachable without a pointer. No new key.

6A show says whether it is in production

Now

The lock is !canEdit || (isShowActive && lockRequested), so it arms whenever any stack runs, including in a build or a tech where cues are fired constantly and edited between GOs. Each host then computes the amber wash itself as !locked && isShowActive, and undo reads the lock slice and the run state on its own.

useEditLock.ts · ShowPage.tsx:168 · PromptBookPage.tsx:180, 633, 648 · Cues.tsx:69 · busking/ShowTab.tsx:63 · history/HistoryMove.tsx:186
Change

A show setting, In production. The lock guards a show that is running and in production; off, the show is always editable, the lock control, the auto-relock countdown and the amber wash never appear, and L does nothing. The rule moves into one place, useEditLock, which also returns unlockedWarning, so no host computes either again.

guarded = canEdit && isShowActive && inProduction

  • Switching it on while a stack runs locks at once, as starting the show does, so turning the guard on never leaves the desk unlocked by surprise. Switching it off while unlocked changes nothing visible but the wash.
  • The header says why there is no lock while a show not in production runs: a quiet, uncoloured Not in production label in the lock control's place, linking to the setting. Without it a missing lock control reads as a bug, and an operator moving between shows cannot tell which one is guarded.
  • The phone runner keeps its layout. It is always laid out as locked; only its ⋯ menu follows the lock, and that now follows the setting too.

7Dragging a selection moves all of it

Now

The sheet kit's row drag moves one row: handleDragEnd splices the active row out and back in at the row it was dropped on, and hands the whole new order to onReorder, which the cue sheet and the Timeline send as one reorder of every entry. The selection plays no part, so with Q11–Q13 selected a drag of Q11 leaves Q12 and Q13 behind.

SheetTable.tsx:291 handleDragEnd · CueSheet.tsx:846 · StackTimeline.tsx:951
Change

rowDrag gains an optional group(activeId): the rows that travel with the one being dragged, in row order. The cue sheet and the Timeline answer with the selected rows when the dragged row is one of them, else the row alone. The kit's new order is a pure function, moveRows(rowIds, group, overId), unit-tested on its own. Still one request: the desk's reorder already takes the whole list.

rowDrag.group · sheetModel moveRows · opt-in per sheet

Rules

  • Which rows travel: the selected rows, if the grabbed row is one of them. On the Table that is the row selection; on the Timeline, the rows the selected cells are in, the kit's selectedRows. Grabbing an unselected row moves it alone and leaves the selection as it is.
  • Where they land: together, in the order they had, before the row dropped on when moving up and after it when moving down, which is where a single row lands now. A selection with gaps closes up. A drop on a row of the block changes nothing.
  • Separators travel too: a selected separator is a row of the stack like any cue, as the single drag already treats it.
  • After the drop the selection stays on the moved rows (their ids are entry ids, which a reorder keeps), so the pane and the bar stay on them. Auto numbers are re-derived by the desk and the out-of-order banner appears if explicit numbers now descend, as after any drag.
  • Refused where a single drag is: locked, or with the Move in dark filter showing only some cues.
  • The landing gap is one row high, because dnd-kit's list strategy moves the other rows for the dragged one only. The drop line and the +n chip say what the gap cannot. A full gap for the block needs a custom sorting strategy; not in this change.
  • Cards have no multi-selection, so their drag is unchanged. The programmer's Stack table and the applied tables share the kit's drag but do not pass group, so theirs is unchanged too.
