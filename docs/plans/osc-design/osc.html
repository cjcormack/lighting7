Design · control surfaces

OSC for QLab

The desk listens for Open Sound Control on the LAN, so a QLab Network cue can GO a cue stack, jump to a cue, press a Look or a busk pad, or move the grand master, through the same actions a MIDI surface uses.

Status Agreed · plan: docs/plans/osc-plan.md Date 7 November 2026 Touches midi/, a new osc/, Install settings, history/

Goals

  • A QLab operator can put the lighting on the QLab cue sheet: each QLab cue sends one OSC message and the desk lands the matching lighting cue.
  • No per-cue setup on the desk. The desk publishes a fixed set of addresses, named after the stacks, cues, Looks and busk pages that already exist.
  • Every OSC action does exactly what the same action does from a MIDI surface or the UI, because it is the same code.
  • The show is unaffected by OSC traffic, whether it is flooded, malformed or silent.

Not in scope

  • Recording, editing, patching or switching projects over OSC.
  • Firing one-shot triggers (confetti, pyro) or running fixture commands (lamp off, resets).
  • MIDI Show Control and timecode. Both are reasonable later doors, but neither is needed for QLab's Network cues.
  • Sending lighting state back to QLab. QLab doesn't read it; feedback is for TouchOSC, in session 3.

How it fits

A MIDI press reaches the show through SurfaceInputRouter, which resolves a BindingTarget and dispatches it through SurfaceActions. SurfaceActions already calls the same CueStackManager, BuskPressService and GlobalScalerState code the REST routes use. OSC joins at that point. Everything upstream of it is new; everything from SurfaceActions down is shared.

Each received message and what became of it goes into a short ring buffer, which the settings page shows as the address log (below).

The address set

Every address starts /lighting7/ and acts on the current project. Segments in braces are names (see Names in addresses) or numbers. exists means SurfaceActions already has the action; new means this work adds it, as a BindingTarget so MIDI gets it too; toggle marks an address whose result depends on the desk's state. Cue sheets should use the explicit forms instead.

A pad press from OSC does what a surface press does, so a generic palette pad lands on whatever the desk has selected, and is refused when nothing is selected (PALETTE_NEEDS_SELECTION) or when the selection's attribute mask leaves out the palette's family (PALETTE_OUTSIDE_MASK). Look and cue pads are the predictable ones to fire from QLab.

A Look is a programmer layer, from OSC as from a busk pad: Clear takes it off, Record captures it, and in Blind it is staged rather than sent, which its log row says. A loose cue (/cue/{cue}/on) is a hold the programmer doesn't touch, so it is the better choice for states the operator mustn't clear by accident.

Continuous values arrive as floats and go straight to the level they set. They don't pass through the 7-bit UByte path MIDI uses, which would throw away most of an OSC float's precision. That is why the grand master, tempo and a stack's FX amount take floats whole. Where a float is wanted any number is accepted, since QLab sends a whole number as an int.

Names in addresses

OSC addresses can't contain spaces, and several other characters (# * , ? [ ] { }) are reserved for pattern matching. Stack, cue, Look and page names contain all of these. So a name appears in an address as its slug: lower-cased, every run of characters other than a–z and 0–9 replaced by one -, the ends trimmed. An incoming address is lower-cased before it is matched. A name with no ASCII letter or digit has no slug and so no address; the address listing says which records those are.

NameSlug
Act 1act-1
Pre-show & walk-inpre-show-walk-in
Finale (wet)finale-wet

Stack names and Look names are already unique within a project, and so are busk page names, but two names can still share a slug ("Act 1" and "Act-1"). When an address matches more than one record it is refused as ambiguous and the log names the candidates. The desk never guesses. Separators in the stack list are never matched, though they may share a stack's name. Cue names are not unique at all, so a /cue/{cue} address only works for a cue whose name is unique. Cues in a stack should be addressed by number instead.

A cue number in an address matches by value, the way the desk sorts cue numbers. 12.5 and 12.50 both reach cue 12.5.

Renaming a stack, a loose cue, a Look or a busk page changes its address, and the QLab cue that sent the old one stops working: the log shows not found. Numbers and positions are quieter. Renumbering a cue, an insert or delete that relabels auto numbers, moving a bank or a pad, or deleting a speed master can point an address at a different record. So every done row names the record it reached, and the desk warns on any of those eight changes when an address it affects has been received since the desk started.

Landing the same twice

A bare GO advances whatever is on deck. If a QLab cue is fired twice, skipped, or the operator goes back in QLab, the lighting and sound fall out of step and stay that way. The same is true of every toggle: a Look press sent twice turns the Look off again.

Recommendation for cue sheets

Program QLab cues with the explicit forms: /stack/act-1/cue/12/go rather than /stack/act-1/go, and /look/haze-fill/on rather than /look/haze-fill/press. Each lands the same state however many times it arrives: a GO TO onto the cue already live, or an on for a Look already on, does nothing, so it doesn't re-fire the cue, reset its FX or fire its events twice. Re-firing a QLab cue repairs the lighting instead of moving it on.

A cue's events (a confetti tube at an offset) fire on GO TO the cue as they do on GO, on the cue's first hold. They never track: a GO TO past a cue fires none of the skipped cue's events, and GO BACK fires none. So a show run with GO TO from QLab fires each cue's events when it lands on that cue, and nothing about events changes for OSC (D11). Events still need the desk armed, which is done at the desk (D6).

The toggles and the bare GO stay in the address set for buttons an operator presses by hand (a TouchOSC GO button, a Stream Deck running an OSC plugin).

A QLab Network cue

In QLab the desk is one Network patch: the desk's IP address, the OSC port and UDP. Each lighting cue in QLab is then a Network cue sending one OSC message on that patch.

Transport

  • UDP first. QLab's Network patches default to UDP, and it's one packet per message. TCP with SLIP framing (OSC 1.1) comes in session 3, when something actually needs it.
  • A hand-rolled parser. OSC 1.0 is small: a null-padded address, a type-tag string starting with ,, then int32, float32, string and blob arguments, big-endian and 4-byte aligned. Bundles (#bundle, a timetag, length-prefixed elements) are unpacked to a depth of 8 and at most 64 messages a packet. Timetags are ignored and every message runs on arrival, which is what QLab sends anyway. Writing the parser ourselves, about 200 lines, keeps the licence gate untouched and matches the desk's own ArtDMX transport. Types the parser doesn't know (h, d, T, F) are read where their size is known, so T/F can work as 1/0, and anything else drops the message with a reason in the log.
  • Its own thread. The receive loop runs on a single osc-1 thread and does nothing but read, check the sender and parse. It never touches the database or the show. It hands messages to a Channel of 64 that drops the oldest and counts each drop in its onUndeliveredElement, unlike the MIDI input flow, whose drops can't be counted (limitation 6 in the surface doc).
  • One collector, guarded. A collector takes each message in turn, resolves it against the current project as a REST request does, and dispatches it inside a per-message guard. A throw, such as one from a project switch in flight, becomes a failed log row and the collector carries on. The same guard goes into the MIDI router, where its absence is a known follow-up.
  • Lifecycle. The listener starts when OSC is enabled in settings, restarts on a port or bind-address change, and reports a bind failure (port in use) in osc.state rather than failing startup.

Security and settings

OSC has no authentication. Anyone who can reach the port can GO the show, so the defaults are strict:

  • Off by default, enabled by an admin on the desk's own listener. The settings route refuses the public listener altogether.
  • A sender allowlist. Each entry is an IP address and a name ("QLab", "Sound op's iPad"). A packet from any other address is dropped before parsing, counted, and shown once per address with an Allow this sender action. That way the first test from QLab tells the admin exactly which address to add. A source address can be forged by anyone on the network, so the allowlist keeps out the wrong machine, not an attacker.
  • A bind address, so the listener can sit on the show network's interface and not on the venue Wi-Fi. The default is every interface, because a desk on one cable is the common case and the allowlist still applies.
  • Never on the public listener or the tunnel. OSC is LAN-only, and ngrok doesn't forward UDP. The settings route and the osc.state frame are both kept off the public listener, so sender names and LAN addresses never leave the building.
  • No arming, triggers, fixture commands, recording or project switches. Those spend something physical, darken lamps for minutes or change stored show data, in a room the sender can't see. A QLab cue can GO a cue whose events fire, but only after someone at the desk has armed it. A stack stop from QLab drops the arm, as any stop does; nothing from OSC can raise it. They aren't in the address set, and the resolver refuses a learned binding to one (session 3).
  • Machine-local. The settings and the allowlist are this machine's. They describe a LAN, so they never sync.

Outcomes and the log

When a QLab cue does nothing, the person at the desk needs to see why in one glance. Every received message is recorded with its sender, address, arguments and outcome:

OutcomeExample detail
DoneGO TO 31 Storm builds in Act 2
DoneAlready live: 31 Storm builds in Act 2
Not foundNo stack act-3 in this show
Ambiguousact-1 matches the stacks "Act 1" and "Act-1"
RefusedBusk pad 1/4 holds a generic palette and needs a selection
FailedThe show was switching; nothing was sent
Bad messageUnknown address /lighting7/stack/act-1/goo; also a type tag it can't read, or a bundle too deep

Most failures happen in the resolver, which returns them directly. A few happen inside SurfaceActions, whose methods mostly return Unit and only log a warning today. Every action the address set reaches returns a small outcome through the shared dispatcher, so its refusals reach the log too. The MIDI router ignores it.

The last 50 entries are kept in memory. Refused senders are a separate list, one row per address with a count, so a flood from one can't push real rows out. A message the queue drops never reaches the resolver, so drops are a count rather than log rows. Every address resolved since the desk started is kept in a set of its own, which the rename and renumber warning reads. A received-message counter, a dropped counter and a refused counter go into the 30-second metrics reporter.

History and undo

Each allowed sender is its own history source: a new HistorySource.Kind.OSC keyed by the allowlist entry, named by it. History shows "QLab" against the programmer steps and show entries a QLab cue causes. A GO isn't a stored write, so most OSC traffic takes no step. A Look on or off does, as it does from a busk pad.

OSC gets no undo address. Undo from QLab would undo whatever QLab did last, which is rarely what the operator at the desk means.

Learnable addresses

Some senders can't be told what to send: a TouchOSC layout someone else built, a show-control system with fixed outputs. For those, session 3 adds an OSC device to the existing binding system:

  • A device type osc whose controls are its bindings' addresses. Bindings are already keyed by (project, deviceTypeKey, controlId, bank), so an address of up to 100 characters (the column's width) is a control id. Every profile today declares its controls in code, so this is the first whose controls are dynamic, which the device registry must allow.
  • An address with a float argument is a continuous control, and one without is a button. A float at 0 is a release, so TouchOSC's momentary buttons work as flashes.
  • MIDI Learn already captures "the next input"; for OSC that is the next address received from an allowed sender.
  • Every BindingTarget is then reachable, apart from the ones refused for OSC in Security.
  • Feedback goes back to the sender's address and port for bound controls: fader positions and button LEDs, through an OscController beside KtMidiController, fed by SurfaceFeedbackPublisher.
  • A /lighting7/reply carrying each fixed address's outcome back to the sender, behind a per-sender switch, for show-control systems that log it.

The fixed /lighting7/ address set is never shadowed by a learned binding. A learned address under /lighting7/ is refused at bind time.

REST, WS and storage

REST

  • GET/PUT /api/rest/install/osc: {enabled, bindAddress, port, senders: [{id, name, address}]}. Admin only. Both are 403 OSC_SETTINGS_LOCAL_ONLY on the public listener; the PUT is 400 OSC_SETTINGS_INVALID for a bad port, address or duplicate sender, naming every problem at once.
  • GET /api/rest/projects/{id}/osc/addresses (session 2): every address the project answers to, with what each does, the record it reaches, any ambiguity and any record with no address. It feeds the Copy OSC address menu items and a printable cheat sheet for the sound department. Any project, both roles.

WebSocket

  • osc.state: outbound only, StateFlow-backed: {enabled, listening, port, error?, received, dropped, refused, refusedSenders, recent: [{at, sender, address, args, outcome, detail}]}. Sent to every signed-in socket on the desk's own listener, since the operator at the desk is the one who needs to see a failed QLab cue, and never to the public listener. An operator's OSC tab is built from this frame alone. Conflated to at most 4 updates a second.

Storage and sync

  • osc_settings (one row) and osc_senders: machine-local, recorded as such in sync/SyncDispositions.kt. No formatVersion change.
  • Learned bindings (session 3) are ordinary control_surface_bindings rows and follow that table's disposition.

Observability

  • A GO is already a cue.go transaction that is always kept, whichever door it came through, so OSC adds no transaction of its own.

Testing

  • Parser: byte-for-byte vectors from the OSC 1.0 specification's examples, plus bundles, bundles past the depth cap, padding edge cases, truncated packets, unknown type tags and an int where a float is wanted.
  • Resolver: slugging, upper case, an empty slug, a separator sharing a stack's name, ambiguity, cue numbers by value, an address for a deleted stack, every row of the address table.
  • Repeats: a GO TO onto the live cue keeps its FX phase and fires no second events; on twice changes nothing.
  • The guard: a dispatch while the show is switching logs failed and the next message still goes.
  • End to end: a real DatagramSocket on loopback sending to the listener, with a recording SurfaceActions (moved into shared test support) standing in for the show. Covers the allowlist, drop counting under a flood, a port that is already in use, and osc.state absent from a remote socket.
  • Show safety: a fade's output timing held under a 10,000-message flood, as CloudOutageOutputTimingTest does for the cloud.
  • Manual: a row in manual-validation.md for real QLab 5 on the show network, with UDP and the explicit address forms.

Decisions

D1

A fixed address set comes first; learnable addresses come later.

QLab sends whatever you type, so a published address set needs no setup per cue. Learn is for senders whose addresses can't be changed.

D2

Every address resolves to a BindingTarget dispatched through SurfaceActions.

There is no OSC-specific show logic: OSC and MIDI share one dispatcher. New actions are added as targets, so MIDI gains them too, and an OSC press does what a surface press does, the desk selection included.

D3

Names appear in addresses as slugs, and an ambiguous match is refused, never guessed.

OSC forbids spaces and reserves pattern characters. A refusal is visible in the log; a guess fires the wrong cue. Separators are never matched. There is no second, exact-name argument form.

D4

Explicit forms sit beside every toggle: GO TO beside GO, on and off beside press.

A QLab cue fired twice must leave the lighting where it was after the first, so a GO TO onto the live cue, and an on or off that is already so, do nothing.

D5

Off by default, senders allowlisted and named, machine-local, LAN-only.

OSC is unauthenticated UDP, and a source address can be forged, so the allowlist keeps out the wrong machine rather than an attacker. Nothing about OSC is served on the public listener. The allowlist entry is also the history source's name.

D6

No arming, triggers, fixture commands, recording, undo or project switching over OSC.

Each either spends something physical, darkens the rig for minutes or changes stored data, for a sender that can't see the room. Arming stays a gesture made at the desk; a stack stop from OSC drops the arm, as any stop does.

D7

OSC acts on the current project only, as MIDI does.

D8

The receive path never blocks on the show.

A dedicated thread that never touches the database or the show, a bounded drop-oldest channel with counted drops, and one collector with a per-message guard.

D9

The OSC parser is hand-rolled: OSC 1.0 over UDP, bundles unpacked to a depth of 8, timetags ignored, any number accepted where a float is wanted.

Small enough to own outright, and it adds no dependency for the licence gate.

D10

Continuous OSC values bypass the 7-bit path.

The grand master, tempo and a stack's FX amount take floats whole.

D11

Cue events keep today's rule.

A GO TO fires the cue it lands on's events, armed, as a GO does; a skipped cue's never fire. An OSC GO TO is a GO TO, so nothing changes.

D12

Every signed-in window on the desk's own listener sees the address log; only admins change OSC settings and the allowlist.

The operator at the desk is the one who needs to see that a QLab cue failed.

D13

The default port is UDP 8415, beside 8413 and 8414, and can be changed.

D14

Replies and feedback wait for session 3.

QLab ignores them. They come with Learn, when a TouchOSC-style sender needs them.

Sessions

Session 1 — Listener, stacks, Looks, cues and busk

Enough for a QLab cue sheet that runs the show.

  • OscReceiver, the parser, settings and the allowlist, the address log and osc.state.
  • The shared dispatcher with its per-message guard, which also closes the MIDI router's.
  • The resolver, for stack addresses (GO, GO TO, standby, back, pause, stop, FX amount), Looks and loose cues (on, off, press), and busk pads and pages.
  • New targets CueStackGoTo, CueStackStandby, CueStackStop, LooseCueSet and LookSet, each a no-op when already so, with outcomes returned.
  • HistorySource.Kind.OSC.
  • Install settings → OSC, for both roles: an operator sees the status and log; an admin also gets enable, port, bind address, senders and Allow this sender.
  • osc-engineering.md and the CLAUDE.md entries.

Session 2 — Masters, tempo and finding addresses

The rest of the fixed address set, and the tools to find each address.

  • Blackout, grand master level, speed master BPM and tap.
  • GET …/osc/addresses, Copy OSC address on stack, cue, Look and pad menus, and a printable cheat sheet.
  • The warning on renaming a stack, a loose cue, a Look or a page, renumbering a cue, an insert or delete that relabels auto numbers, moving a bank or pad, or deleting a speed master an address reaches.

Session 3 — Learnable addresses, feedback and TCP

Gated on someone using TouchOSC or another fixed-output sender.

  • The osc device type, Learn over OSC, and the refusals for /lighting7/ and the targets excluded in D6.
  • OscController feedback to bound controls, and /lighting7/reply with each fixed address's outcome, behind a per-sender switch.
  • TCP with SLIP framing.
