Every change can be taken back

Every other desk has an Undo key. lighting7 has about ten separate one-step Undos, each built for one place, and none of them reaches a deleted cue, a cleared programmer or an edit Claude made. This design gives the desk two histories behind one key. The programmer's history is a run of snapshots. The show's history is a journal of every stored record that changed, which can be put back in place without a reload. One header control, one History sheet and ⌘Z drive both.

Chris answered the seven questions in §4 on 2026-10-20, taking the recommended answer each time. The implementation plan is docs/plans/undo-plan.md; where they differ, the plan wins on behaviour and this page on layout and copy. The fixture, cue and Look names in the mock-ups are illustrative.

The model: two histories, one key§3

The programmer and the show are different kinds of state. The programmer is one shared, live thing, and its history is a run of snapshots: going back one step restores what it held before the last gesture, whoever made it. The show is stored records, and its history is a journal of record changes, each with a source. Any entry can be put back on its own, provided nothing has touched those records since.

Rows

  • The label comes from the route or tool when it gives one (Record Q13 into Act 1), else from what changed (Look “Warm wash”: 4 values).
  • Counts: + records added, − removed, ~ changed.
  • Chips: live in Q11 where an undo would change output now, and changes output for patch, park and universe changes.
  • Clicking a row expands it to the records it touched, each a link to open (a cue, a Look, a fixture).

Undo back to here

  • On your own row: undoes it and every later change of yours, newest first, in one transaction.
  • A later entry from another source that touched the same records is listed in the confirm (§5.5) and goes too.
  • On someone else's row the button says whose it is: Undo Claude's change.
  • An operator gets read-only rows on a venue, matching the write guard.

A long press or right-click on Undo opens the last steps. Picking one goes back to before it.
  • What a step captures: the slot stacks and sideband, the layers and Include state, the Local effects (as specs with their phase), Locate and the programmer's scenery. The Blind flag and the selection are left out.
  • What counts as one step: one gesture from any door, whether a WS frame, a press, a spread, an aim, an MCP set_programmer or a surface move. A continuous move (fader, encoder, colour picker) on the same property merges until 1 s of rest.
  • How it lands: at the Clear fade shown beside Clear, so undoing a 1 s Clear brings it back over 1 s. Effects grow back as a press would.

How it works§6

The design rests on four pieces, and none of them needs the ~300 write sites to change. They are a write origin set at each door, a cache of every record in canonical form, a statement hook that says which tables a commit touched, and a per-kind codec that can put a record back exactly.

Write origin

A WriteOrigin(projectId, source, window, requestId, label?) carried as a ThreadContextElement, so the interceptor sees it on the transaction's thread. It is set at four doors:

  • A route-scoped Ktor plugin under /projects/{id} and the FX routes. It takes the account from the session and the window from an X-Desk-Window header that restApi's base query adds (the registry row id).
  • The WS dispatcher, per frame, from SocketScope.
  • McpProtocol.callTool, from the grant and its clientName.
  • SurfaceInputRouter, as the surface.

A route or tool may name its entry with historyLabel("Record Q13 into Act 1"). A write with no origin (the tempo flush, the scheduler) makes no entry.

Record cache and diff

The exporter's writeJson(dir, …) becomes a RecordSink, either a folder or an in-memory map. A project's cache is built on first use, at about 100 ms for a 300-patch rig. Inside each write's transaction, just before it commits, only the touched kinds are re-exported and diffed by hash against the cache. Once it commits the cache takes the new values, and an empty diff produces no entry.

Each change stores (folder, uuid, rowId, before?, after?). Canonical JSON keeps entries small, and a typical edit is a few KB.

RecordCodec: putting records back

The importer's per-kind functions are refactored to read from a RecordSource (a folder or a map) and to take an upsert mode that seeds the uuid→DAO maps from existing rows. In that mode a record whose uuid exists is updated in place, a missing one is inserted with its old row id, and an absent one is deleted in the importer's own foreign-key order.

The database's own constraints catch a collision (a key someone has since reused). The undo then rolls back whole with HISTORY_UNDO_BLOCKED, naming the record.

KindEffects: what an undo sets off

One table maps each kind to what its original write would have done:

  • Looks and palettes: republish.
  • Cues and their children: markEdited, cuesRecomposed.
  • Entries and stacks: cueStackListChanged and the run state.
  • Patches, groups, universes, hides, overrides and colours: loadFixtures.
  • Speed masters: reloadSpeedMasters.
  • Parks: ParkManager reload.
  • Busk pages: buskLayoutChanged(pageIds).
  • Stage and scene: their frames and the scenery recompute.
  • Scripts and FX definitions: recompile.

Programmer snapshots

ProgrammerStore.snapshot() / restore(snap, fadeMs) are new. They capture slots, sideband, layers and Include state, leaving out the epochs and Blind. Beside them go LocateManager's active map, ProgrammerScenery.Snapshot and the Local effects as specs. ProgrammerHistory keeps a ring of 50 and checkpoints before each gesture at the same doors, coalescing by (source, property, target) within 1 s.

The wire

  • GET /projects/{id}/history: the History sheet's list.
  • POST …/history/undo {entryId?, backToHere?, programmerOnly?} and …/redo. These answer 409 HISTORY_CONFLICT (with the colliding entries), HISTORY_NOT_YOURS, HISTORY_UNDO_BLOCKED or HISTORY_EMPTY.
  • history.state: an outbound, per-socket WS frame, {undo, redo, revision} for this socket's source. The sheet refetches when revision moves.
  • Undo is REST only, so the socket gains no operation. Each REST answer carries X-History-Entry, which a toast's Undo names.

What it covers§7

The show's history covers exactly the records sync covers. A test ties the journal's kinds to SyncCoverageTest's portable dispositions, so a new portable table is journaled or the build fails.

Can be undone

  • Cues, entries, stacks, markers, layers, rows, events, scenery, speed-master lists
  • Looks, palettes, busk pages and rig, cue slots
  • Patch, groups, universes, riggings, regions, hides, overrides, recolours
  • Stage elements, viewpoints, prompt books and their markup
  • Scripts, FX definitions, speed masters' stored fields, bindings
  • Parks and releases (P5)
  • The programmer: values, layers, Local effects, Locate, its scenery; Clear, Release, Include, press, spread, aim, focus, Detach

Not undoable

  • GO, BACK, GO TO, standby, holds, stack FX size (playback, as on every desk)
  • Arm, fire, fixture commands, bulk lamp runs (Make rig safe keeps its own Undo)
  • Grand master, tempo taps and BPM moves, Blind, the selection, window layout
  • Machine-local settings: universe addresses, Full detail, tube state, remote access
  • Sync, venue publish, Update, Attach, Detach, Extract, Discard (each is a clear point)
  • Creating, deleting or switching projects; accounts and install settings

Risks and things to watch§9

  • The importer refactor is the big piece. Moving it from folders to records must not change a byte of import. The round-trip, clone and venue tests already pin that, and session 4 adds the undo-is-identity test over every kind in RichProjectFixture.
  • Raw restore skips route validation. It restores a state the records were in, but other records may have moved since. The conflict check covers the same records and database constraints cover keys. A rule held only in route code (a venue key clash, a group with a member hidden since) needs the checks Update uses (VenueRigChecks) run after the restore and before commit.
  • A write that touches a project other than the current one (MCP with a projectId) must carry that project in its origin. The interceptor sees tables, not projects.
  • Background writes. The tempo flush writes a speed master's BPM with no person behind it. Writes with no origin make no entry, and the records they change are rebased into the journal, so a tap never reads as a conflict.
  • Memory. The record cache is one canonical copy of the project, a few MB at most, and the journal is capped by P3. Both are dropped when the project's history clears.
  • Follow-up gates. FU-AUTH-WS-PER-MESSAGE fires when an admin-only operation gains a WS command. Undo is REST only and history.state is outbound, so it does not fire.

Out of scope§10

  • Undoing playback, or a "last GO" recovery, which belongs to the Show view's BACK.
  • A history that persists across a restart, or travels with sync.
  • Branching history or merging an undone branch back.
  • Undo inside the Stage editor's drag, which keeps its own handles. Its committed placements are journaled like any patch write.
