Design · cloud sync

Snapshot Restore

The sync page's History lists every snapshot of a show, but nothing on the desk can go back to one. This design adds Restore: review what an old snapshot would change, then make it the show again as a new commit, which every other desk on the repo takes on its next sync.

Status Agreed · plan: docs/plans/completed/sync-restore-plan.md Date 7 November 2026 Touches sync/, routes/cloudSync.kt, state/VenueHoldService.kt, frontend/src/components/cloudSync/

Goals

  • An admin can pick any snapshot in a show's History and see, record by record, what going back to it would bring back, take away and change.
  • Restoring makes the show exactly what that snapshot holds, read by today's importer, without touching git by hand.
  • The restore travels: every desk on the repo ends up on the restored show, without anyone force-pushing or rewriting history.
  • A restore can be taken back, because the show as it stood just before is always a snapshot in History too.
  • A running show is never dipped or blacked out by a restore. It reloads the way a sync pull does.
  • No network is needed to restore. The local repo holds every snapshot, so a desk at a venue without internet can still go back.

Not in scope

  • Venues. A venue's repo holds its published versions, and its draft never syncs. Going back to a version is a separate question for the venue's own History.
  • Machine-local settings: universe addresses, the grand master, remote access. A restore leaves them as a pull does.
  • Restoring one cue, Look or palette on its own. That is session 3, Bring back selected.
  • An MCP tool. Restore is an admin's decision at the desk.

What there is today

Every snapshot is a git commit in the project's working tree (sync/{projectUuid}/repo/), one canonical-JSON file per record, written by SnapshotEngine's wipe-then-export. HistoryPanel reads GET …/sync/log and shows commit, time, desk and message. It has no actions.

Going back today means doing it outside the desk: in a clone, rebuild an old commit's tree as a new commit, push it, and press Sync now, which fast-forwards and rebuilds the project through ProjectImporter.replaceFromWorkingTree. That works. It also needs git, gets binary files and deletion markers wrong easily, and gives no idea of what will change until it has.

Two pieces already in the engine do most of the work:

  • replaceFromWorkingTree rebuilds a project from a tree in one transaction, reads every older formatVersion, refuses a pin the desk lacks, keeps the machine overrides keyed to the project, and clears the show's undo history with a reason.
  • SnapshotEngine.snapshot writes a deletion marker for every record sync_state knows that the database no longer has. A restore that goes through the database gets its deletion markers right with no new code.

Each History row gains a menu. Review and restore… opens the review. Copy commit id is there for someone who wants to look in git. The newest row's restore is disabled: it already is the show, apart from edits made since, which a snapshot captures.

The review

The review answers one question: if I restore this, what happens to the show? It groups changes by kind of record, using the names the desk's own History already gives them (RecordLabeler), and says three things the record list can't: the project's name, its venue pin, and what the live show will do.

The comparison is made in today's format. The review runs the restore inside a transaction and rolls it back: it exports the project now, imports the snapshot's tree with today's importer, exports again, and compares the two exports record by record. A snapshot written in format v31 is compared as v49 would write it, so a renamed field doesn't count as a change. Extract, Detach, Attach and Update all build their reviews the same way.

Opening the review changes nothing, so it also serves as what has changed since this snapshot.

What a restore does

Under the per-project sync lock, so a restore never overlaps an auto-sync tick, a Sync now or a conflict session:

1 · Sync firstWith a repo attached and reachable, the ordinary sync pipeline runs, so the restore starts from the latest show across desks. It snapshots any edits first, as every sync does. A sync that opens a conflict session, or fails for any reason but an unreachable repo, refuses the restore. If the repo can't be reached, the desk restores locally and says so.
↓
2 · Check the reviewThe review is computed again. If it differs from the one the admin confirmed (another desk's change came in at step 1, or someone edited the show), nothing is written. The answer is 409 with the new review, to confirm again.
↓
3 · SnapshotEdits the first sync didn't commit (there was no sync, or one landed since) are committed as Before restoring 3f2a91c. Either way, the newest commit is now the show as it stood.
↓
4 · Import the snapshotIn one transaction, which holds off every other write: if the show still matches that commit, replaceFromWorkingTree rebuilds it from the target's tree (extracted with JGitClient.extractTree, binaries included), and the history reason is Restored a snapshot. If a write landed in between, the restore stops with a fresh review. Its scene images and prompt-book PDF are copied into the local stores, so a picture pruned since comes back.
↓
5 · Snapshot againSnapshotEngine writes the restored database as Restored 3f2a91c from 2026-10-29 21:14 UTC, with the note if there is one. Deletion markers come from sync_state, as for any deletion, and the commit is in today's format.
↓
6 · ReloadIf the project is the live one, switchProject(id, reload = true) carries the running show across.
↓
7 · PushA plain push of a local-ahead branch, as Sync now would do. On a pull-only desk, or one that can't reach the repo, the restore stays local and goes out on the next sync.
NewExisting engine, reused

The ordering keeps the fast-forward's failure mode. If the desk dies between steps 4 and 5, the database is ahead of git. The next snapshot writes the restored show and nothing is lost. The activity log gets a RESTORED row naming the target and the counts.

A commit forward, never back

A restore never moves the branch backwards. It adds a commit on top whose content is the old snapshot's, and its parent is the show as it stood just before. Every other desk reaches it by a fast-forward or a three-way merge, which the engine already does correctly. A reset and force-push would leave every peer diverged with nothing shared to merge against, which is the situation Phase 5 removed force-push to avoid.

Other desks

What another desk on the same repo does on its next sync after the restore is pushed:

That deskWhat happens
Has no unsynced editsFast-forwards to the restore and rebuilds, exactly as this desk did. Its live show reloads.
Has edits to records the restore didn't touchThree-way merge with no conflicts. Its edits are kept on top of the restored show.
Has edits to a record the restore changed backA conflict on that record, shown in its Conflicts panel as any edit-edit conflict. Remote takes the restored version.
Still has a record the restore takes awayThe restore carries a deletion marker for every record that was synced, so the record goes. If that desk edited it meanwhile, it's an edit-delete conflict.
Deleted a record the restore brings backThe record comes back: the restore is a later change than the deletion. An edit on the other side surfaces as a delete-edit conflict.

Syncing first (step 1) is what makes this table short. Without it, a change another desk pushed after this desk's last sync, to a record the restore leaves alone, would survive the restore without the admin ever seeing it.

The live show

A restore of the current project reloads it with reload = true, as a sync pull does. The rig holds its levels, live cues are GO'd again, the programmer and hand-run FX come back, and what changed crossfades in over RESUME_FADE_MS. A cue or stack the snapshot lacks is dropped from the carry, as after a pull that deleted it.

One change to the venue hold

A restore can move a show's pin back, from v5 to v3 in the mock. A sync pull that moves the pin judges the hold afresh, and a show behind its venue on output is held: every channel at zero but parks. Mid-show that would be a blackout. So a restore that leaves the live show behind on output does what a publish does to a running show: it keeps running against its restored pin, guarded, and opens held next time. The restore records that before it reloads, with the runAgainstOnLoad call Attach already makes. The review says so in advance.

A restore whose snapshot pins a venue version this desk doesn't hold is refused with VENUE_MISSING before anything is written, naming the venue and its repo. Versions only ever accumulate on a desk, so this needs a desk that never imported that version.

Undoing a restore

⌘Z can't take back a restore: rebuilding a project mints new row ids, so replaceFromWorkingTree clears the show's undo history, as a pull does. The History sheet shows that as a clear point, Restored a snapshot.

The sync history covers it instead. The commit before the restore is always the show as it stood, so undoing a restore is restoring that commit. The done toast offers it straight away:

Restored to Thu 29 Oct, 21:1414 records changed · pushed to the repo Undo

Undo opens the same review for the commit just before the restore, which shows the same changes in reverse. Later on, that row in History does it.

Who, when, and what not

  • Admins only. Every sync route is mounted inside adminOnly in routes/projects.kt, and the restore routes join them. This holds on both listeners, as for Sync now.
  • Shows only. A venue answers VENUE_DRAFT_NOT_SYNCED, as its snapshot does. A version's sync subtree already answers VENUE_VERSION_READ_ONLY.
  • Not during a conflict session: SESSION_PENDING, as a snapshot.
  • Only a commit in the branch's history. The sha must be an ancestor of the head the History panel lists. Anything else is RESTORE_COMMIT_UNKNOWN.
  • Nothing to do: when the snapshot is what the show already is, the review says so and Restore is disabled (RESTORE_NO_CHANGES).
  • Untouched: sync_configs, the grand master and blackout, the effects arm, remote-access settings and runtime state, which all survive a pull and survive a restore for the same reason. In production keeps its current value, as a merge keeps this desk's, so a show locked for a performance stays locked.
  • Universe addresses are machine-local, keyed by project. A restore to before an Extract makes universes the show's own again whose addresses the venue now holds; the restore copies them back, as Detach does. A restore to before an Attach can bring back universes with no address on this desk; the review names them.
  • Show settings (name, description, stage size) come back and are listed in the review. If another project now has the old name, the show keeps its current one and the review says so.
  • Independent of GitHub. A restore reads the local repo and pushes through the sync engine, so it keeps working when GitHub sync gives way to Lighting7 Cloud's hosted git (PRD G-5).

REST

Two routes under the existing /api/rest/projects/{id}/sync/, admin only. There is no WS operation. The reload and the sync fire the frames a pull already fires.

RouteWhat it does
GET …/sync/restore/{sha}The review, changing nothing: {target, head, token, counts, kinds: [{folder, noun, records: [{uuid, label, change: BACK | GONE | CHANGED}]}], project: {name?}, venue?: {now, then, behind}, live, sync: {lastSyncedAt, repo, push}, noChanges}
POST …/sync/restore{sha, token, note?}: steps 1–7. Answers {commit, before, counts, sync?, notes}, where sync is the push's SyncRunResult, or absent when it was skipped, with the reason in notes.
CodeWhen
404 RESTORE_COMMIT_UNKNOWNThe sha isn't in the branch's history.
409 RESTORE_REVIEW_STALEThe restore would now do something other than the review the token names. The body carries the new review.
409 RESTORE_NO_CHANGESThe snapshot is the show as it is.
400 RESTORE_INVALIDA note over 200 characters or with a line break; a blank sha or token.
422 RESTORE_TOO_OLDThe snapshot's format is older than this desk reads.
422 RESTORE_UNREADABLEThe snapshot's tree can't be imported for another reason.
409 SESSION_PENDINGA conflict session is open, or the first sync opened one.
409 VENUE_MISSINGThe snapshot pins a venue version this desk lacks.
409 VENUE_DRAFT_NOT_SYNCEDThe project is a venue.

The token is a hash of the review's content (target, counts and every record's change), not of the head. A snapshot that moves the head without changing what the restore would do keeps the token valid.

Bringing back one record

The commonest case is probably I deleted that cue on Tuesday, and a whole-show restore is a blunt answer to it. The review already lists every record. Session 3 puts a check box beside each and adds Bring back selected:

  • It applies through ProjectImporter.restore, the upsert that ⌘Z's undo uses. Row ids are kept where they can be, there is no whole-project reload, and KindEffects runs what the records' writes would have run.
  • It is journaled as an ordinary show-history entry, so ⌘Z takes it back. It is a normal edit, so the next sync carries it like any other.
  • A chosen record pulls in what it needs that the show lacks: a cue its stack entry, a Look layer its Look and the palettes that Look references. The review lists these as also needed before anything is applied. A name now taken refuses, as an undo does (HISTORY_UNDO_BLOCKED).

It shares the review and the extraction with sessions 1 and 2 but none of their writing path, which is why it is a separate session that waits on them.

Testing

  • Round trip (SnapshotRestoreTest, on RichProjectFixture): snapshot, edit, add, delete, snapshot, restore the first. The project exports exactly as the first snapshot imports today. The restore commit carries deletion markers for synced records created since, and records deleted since come back live.
  • Older format: a frozen tree at an older formatVersion restores, and the review counts no record as changed for its format alone.
  • Binaries: a scene image removed from the store comes back from the target's tree, and so does a prompt-book PDF.
  • Two desks, over a bare repo as RemoteSyncEngine's tests do: the peer fast-forwards; the peer with an unrelated edit merges cleanly; the peer that edited a restored record gets one conflict.
  • Refusals: an unknown sha, a stale token (with the new review returned), no changes, an open conflict session, a first sync that fails other than offline, a venue, a missing venue version and a snapshot too old to read. The database and the branch are unmoved by each.
  • Settings and addresses: a snapshot that differs only in stage size is listed; In production stays on; a taken name is kept; a show restored to before an Extract gets its addresses back.
  • Live show: the current project reloads with carry, and a restore that moves the pin behind on output leaves the running show unheld.
  • Offline and pull-only: an unreachable remote restores locally and reports the skipped push; sync.push = false commits locally and never pushes.
  • Frontend: the History row menu, the review's groups and notes, the stale-review retry, and the toast's Undo.

Decisions

D1

A restore is a new commit on top of the branch, never a reset or force-push.

Peers reach it by fast-forward or three-way merge. A rewritten history leaves every peer diverged.

D2

A restore goes through the database: the target tree is imported by today's importer, and the next snapshot writes it.

Deletion markers then come from sync_state as for any deletion, the commit is in today's format, and an older snapshot is read the way an older archive is. Copying the old tree into git directly would get both wrong.

D3

The show as it stood is always a commit before the restore, and undoing a restore is restoring that commit.

⌘Z can't reach across a whole-project rebuild. The sync history can.

D4

The review is the restore, rolled back, compared record by record in today's format.

The same shape as Extract, Detach, Attach and Update. Hashing the two git trees would count every format change as an edit.

D5

The restore syncs first when the repo can be reached and pushes after. Offline, it restores locally.

Syncing first means the review covers every desk's changes. Only an unreachable repo lets the restore go on without it, so the network never stops a restore, and nothing else is papered over.

D6

The confirmed review's token guards the write. A restore that would now do something else is refused with the new review.

The token hashes the review's content, so a change that alters nothing in the restore doesn't trip it.

D7

The venue pin, and the show's other settings, are restored with the rows.

Hides, overrides and recolours name the pinned version's records, so rows from v3 under a v5 pin would be a show that never existed. See Q2.

D8

A live show reloads with carry, and a restore never holds a running show.

Behind on output after a restore, it runs against its pin as after a publish, and opens held next time.

D9

Shows only, admins only, REST only.

A venue's history is its versions. Every sync route is an admin's. No WS operation and no MCP tool.

D10

Bringing back individual records is session 3 of this plan, built on undo's upsert.

It needs a dependency closure and a journaled entry, which the whole-show restore doesn't.

D11

A restore may carry a note, up to 200 characters on one line, appended to its commit message.

History then says why the show went back, as a snapshot's message does.

Asked and answered

  1. Should a restore sync before it starts and push when it's done (D5), or stay local until the next Sync now?

    Sync first and push after. A local-only restore would surprise the next person who presses Sync now on another desk.

  2. Should the venue pin come back with the rows (D7), or should the show keep its current pin?

    The pin comes back. Keeping today's pin under old rows would need Update's review and its drift decisions; restore, then update already does that in two steps.

  3. Is Bring back selected (session 3) part of this plan, or a follow-up?

    Session 3 of this plan, run once sessions 1–2 have been used on a real show.

  4. Should a restore offer a note, like Take snapshot's message, to say why?

    Yes, optional, appended to the restore's commit message (D11).
