# Planning prompt

Paste into a Claude Code session in `lighting7` (the plan lives there, and the backend half is the
larger half). It produces a plan, not code.

```
Write the implementation plan for the multi-screen desk, as docs/plans/multi-screen-plan.md, from
the design record at docs/plans/multi-screen-design/ (read INDEX.md first, then Model.dc.html and
Survey.dc.html, then the three screen artboards Main / Screen2 / Tablet, then Screens.dc.html,
Hand.dc.html and Options.dc.html; the artboards are generated by gen.mjs and render standalone in a
browser). The record is a proposal: it makes five calls, listed in INDEX.md under "The calls this
record makes". Treat them as made unless one of them turns out to contradict the code — then say
so in the plan's decisions section and pick, with the reason, rather than asking.

The plan's shape is the house shape — read docs/plans/completed/busk-layout-plan.md and
docs/plans/completed/midi-surface-plan.md first and match them: §Context (what exists, what the
brief asked, what the record found), §Decisions taken (numbered D1…, each with its reason and what
it rules out), §The model (the desk facts and window facts, every new frame with its exact shape,
who emits it and when, and what each client does with it), §Session split (each session a shippable
whole with its own desk check, backend and frontend named per session, ordered so the earliest
session is useful alone), §Desk checks (staged, in the manual-validation.md format), §Follow-ups
(anything deferred, with an FU- id). Terse done-markers only; the detail belongs in commit messages.

Ground every claim in the code before writing it. On this side: the selection (models/selection.kt
or wherever `selection.state` is emitted, `fx/TargetCoverage`, the StateFlow that broadcasts it and
clears it on project switch), `BuskPressService` and `POST /busk/pads/{id}/press` (it already reads
the desk selection server-side — say exactly what changes when the selection carries a family
mask), `ProgrammerLayerStack.toggle` and `POST /templates/{id}/apply` (the same question), the
per-connection scope the speed-master beat subscriptions live on (the windows registry wants the
same lifetime), `busk.pageState` / `busk.setPage` (the precedent for one window moving another's
state), `midi/` bindings and `BindingControlKind` (Pick up / Place as button bindings), and
`ControlSurfaceBindingService.resolve`. In ../lighting-react: src/api/selectionApi.ts and
src/store/selection.ts, src/components/fixtures-list/useDeskSelectionBridge.ts (the echo FIFO —
the mask must ride the same publish or the bridge's "is this frame mine?" breaks), the cell
selection model in src/components/sheet/ (what a marquee knows about its columns and when it
publishes), src/components/busking/TargetBand.tsx and lookPresence.ts, src/components/dnd/
(DeskDndProvider, dragOverlayRegistry, slotDrop.ts — the hand's drop targets are these droppables
plus the layer stack), src/components/UserMenu.tsx and the command palette, src/Layout.tsx (the
header row is full; nothing new goes there), src/store/status.ts (the reconnect resync — a
windows-registry entry must re-announce on reopen), src/main.tsx and the PWA situation (is there a
manifest at all today), and CLAUDE.md §"Where a WS bridge subscribes" for where each new bridge
goes. Where the record names a file that does not exist, say what does.

The plan must answer, explicitly:

1. The wire. `selection.state` gains `families` and per-target cells, and `source` (the window
   that moved it); `windows.state` / `windows.announce` / `windows.show`; `hand.state` /
   `hand.pickUp` / `hand.place` / `hand.drop`. For each: the Kotlin model, the JSON, whether it is a
   StateFlow snapshot-and-broadcast like selection.state or a keyed delta, what happens on
   reconnect, on project switch, and when the record behind a held item is deleted. Decide whether
   the mask is a property of the selection (one desk fact) or a second fact beside it, and why
   (the record says one fact; check what a MIDI select button or `selection.toggle` should do to
   the mask).
2. Where a press lands. With a mask on the selection, list every consumer of the desk selection
   server-side and say for each whether it honours the mask (a template apply masks to its own
   family already — is the intersection what the operator expects?), ignores it, or refuses. A
   Look pad holding position rows pressed while the mask is Colour: skip, refuse by name, or apply
   all — pick and say why, and how the client reports it on the window that made the marquee.
3. Follow / local per window. What the flag gates on the client (publish, apply, or both), where it
   is stored, what the desk chip shows, what happens to a shared selection at the moment of
   unlinking, and how Record scopes when a window is unlinked. Confirm the record's default-on call
   against the plain list routes' existing rule.
4. The windows registry. What a window is (a socket, a tab, a browser?), how it gets a name and
   keeps it across reloads (a per-browser id in localStorage announced on every open), what
   `windows.show` does on the receiving window (a navigate — say how it interacts with the show-
   editing lock and with an open cell editor), what the Screens sheet shows for a window that is
   not this one, and whether "Open on Display 2" is client-only (Window Management API, Chrome, a
   permission prompt) with the registry learning about the new window when it announces.
5. Full screen. The user-menu item and the ⌘K command on requestFullscreen; feature-detected
   Keyboard Lock for Esc in Chrome; a manifest with display: fullscreen and standalone fallback;
   the "Return to full screen" banner after reload; what the desk's Windows install does about
   per-screen shortcuts (Windows installer builds only — see docs/windows-updates.md). State what
   Safari on iPad does and does not do, from MDN, not from memory.
6. The hand. One held item per desk; pick-up replaces; what "place" means per target kind (a busk
   bank via the layout PUT, a cue slot via the slot mutation, the programmer layer stack via
   addLayer, a cue's stack via record/patch) and which of those the existing mutations already
   cover; the auto-drop timeout; Undo on the placing window; what the ghost draws (the frozen
   PadFace, per padFace.ts) on every window; the MIDI bindings. Then the same-machine edge drag
   as its own session, last, gated on Window Management being available, with the fallback being
   the hand — say precisely where the drag leaves dnd-kit and becomes a pick-up.
7. What this rules out. No window-to-window messages; no second programmer per user (a later
   plan, and name what it would need); nothing new in the app header row; no HTML5 native DnD
   unless a session after the hand chooses to add it as the desk-machine fast path (Options B).

Size the sessions so the first ships the wire and the desk chip alone (mask + source on
selection.state, the chip on the bar, follow/local), the second the windows registry with Full
screen and the Screens sheet, the third the hand, the fourth the edge drag; each with its own desk
check on the real two-screen desk and an iPad. Name the tests each session adds on both sides,
including the maskPicker-style pin between the Kotlin and TypeScript mask vocabularies. Note every
place CLAUDE.md on either side will need a paragraph, but do not write them yet.

Do not write code, do not commit. Finish by listing the questions only Chris can answer, if any
remain after reading the code — there should be few, and none that the record already called.
```
