One cue, many stacks

A cue becomes a project record of what a state is. A stack becomes an ordered list of entries that each name a cue. Edit a cue once and every stack that uses it changes. A cue can sit in no stack, and deleting one is its own deliberate act.

The engineering plan is docs/plans/completed/cue-model-plan.md; this page is its one-page copy, checked in as docs/plans/completed/cue-model-design/cue-model.html. Where they differ, the markdown wins.

The problem§1

On the first evening in the hall, the same blackout ended every act, and each act's stack held its own copy. Fix one and the others stayed wrong. Today a cue can't be shared: its place in a stack is written into the cue itself.

Decisionsagreed 2026-10-14, four rounds

#Decision
D1One shared cue. A stack is an ordered list of entries naming cues. A cue may be in no stack (loose). Removing an entry or deleting a stack never deletes a cue.
D2An entry holds position, number (and auto) and follow. The cue holds everything else, fade included: one fade per cue.
D3A cue live in two places is one contribution, held until the last. It fades in on the first hold and out on the last release.
D4Prompt-book anchors are per entry: a cue used in two acts is anchored at each place.
D5Existing data arrives by a recovered startup migration, with a backup copy first.
D6Busk pads, cue slots, MIDI FireCue and the hand name the cue and run it loose: no follow, no tracking.
D7A cue may appear twice in one stack. Everything keys on the entry.
D8Deleting a cue in use is 409 CUE_IN_USE naming every reference; ?force=true takes them with it. The UI always confirms with the list.
D9Copying from another show is mapped by key, venue records by uuid first, across versions. Unresolved rows are reported, after a dry run.
D10Loose holds compose above every stack, newest press on top.
D11A cue pad is solid when held loose and outlined when live only through a stack. A press toggles the loose hold.
D12A marker is a labelled entry, not a cue.
D13The all-cues table is its own nav item, beside Looks and Templates.
D14Numbering is per entry; an explicit renumber never relabels its auto neighbours (venue-visit D11).
D15A cue's events fire when it comes on, on its first hold. A GO into a cue already live elsewhere fires nothing.
D16Removing the live entry leaves the stage alone; the stack's next GO fires the entry that followed it.
D17A stack delete offers to delete the cues it would leave loose, unticked by default.
D18Any project can be a copy's source; venue records match by uuid when both are on the same venue.

The model§3.1–3.3

The entry · its place in a stack

  • position (an ordinal, a double)
  • number, and whether it is auto
  • follow: auto-advance and its delay
  • or, for a marker, a label and no cue
  • its prompt-book anchor

The cue · what the state is

  • name, notes, stomp
  • fade time and curve
  • layers, values, ad-hoc effects, triggers
  • scenery and cue events
  • (and the speed masters S16 adds)

Getting there from today's data

One startup migration, run once when cues still has cue_stack_id. It runs before the schema reconciliation, because SQLite can't add a NOT NULL column to a populated anchors table.

StepWhat happens
BackupVACUUM INTO <db>.pre-cue-model-<utc>.db, outside the transaction.

Again?A second start finds no cue_stack_id and does nothing.

Runtime: holds§3.4

Anything that makes a cue live takes a hold on it: a running stack whose live entry names the cue, or a loose press. One registry, fx/CueHolds.kt, decides when the cue fades in, when it fades out, and at what priority it composes.

Where a held cue composes

Its priority is the highest of its holds. A loose press sits above every stack (D10), so a pad beats the playback on any property both set.

Basethe patch's defaults
  • Standby, next, GO TO and Preview name an entry, so a cue twice in one stack is never ambiguous. A crossfade between two entries of the same cue moves nothing.
  • Scenery tracks down a stack's entries to its live entry. A loose cue folds in like a one-cue stack, in GO order.
  • Pads read the new outbound frame cueHolds.state: solid held loose, outline live through a stack.
  • Cue events fire when the cue comes on, on its first hold, labelled with the entry's number (D15). A GO into a cue already live elsewhere fires nothing.

Removing and deleting§3.6

  • Remove from stack deletes the entry and its anchor, and renumbers that stack. The cue stays, loose if that was its last entry. Removing the live entry changes nothing on stage until the stack's next GO, which fires the entry that followed (D16).
  • Delete a stack deletes its entries and its set. Its cues stay, and the confirm offers Also delete the N cues no other stack uses, unticked (D17).
  • Delete a cue in use is 409 CUE_IN_USE, listing every entry, pad, slot, anchor and binding. With force, all of them go with it, and every hold is released first. The card's Remove becomes Remove from stack; delete lives in the Cues table.

Copying from another show§3.8

A copy is a new cue in the target, loose or into a chosen stack. It reuses copy_to_project's copier, cut down to cues.

  • Fixtures and groups are already named by key; anything the target's rig lacks is kept and marked, as an Update's dead references are.
  • Venue records match by uuid first. Two shows on one venue share its records' uuids across versions, so a cannon event or a tab's scenery resolves even one version apart. A show's own patch maps by key, and its own element by name.
  • Looks and templates link by name or are copied; speed masters by index; scripts by name. A dry run answers the same thing rolled back.

Any project can be the source (D18); from a show off the venue, everything maps by key and name. It replaces POST /cues/{id}/copy, which left the source project's Look ids on the copy's layers.

Seven sessions, one PR each§5

Sessions 1 and 2 keep one entry per cue, so a v27 archive can still describe the desk. Sync lands in session 3, before session 4 lets a cue be shared or loose.

  1. Entries and the migrationbackend + frontend

    The new table, the startup migration with its backup, numbering on entries, markers as entries, anchors on entries. Behaviour unchanged; the exporter still writes v27. Chris runs it on a copy of the desk's database first.

  2. Holdsbackend + frontend

    CueHolds under the manager, the crossfade, the cue layer, triggers, scenery, events and the show carry. Pads, slots, FireCue and the hand run loose. Entry-keyed standby and run state, cueHolds.state, the pad's two looks.

  3. Sync v28backend

    Entry files, double ordinals, auto numbers left out, anchors by entry, the v27 reader, the number-clash rule.

  4. Sharing and explicit deletebackend + Show view

    Add shares; remove from stack; a stack delete leaves its cues; delete with its guard; Record without a stack. The in N stacks chip and the new card actions.

  5. The Cues tablefrontend + backend

    The library view, its filters and its multi-select actions.

  6. Copy from another showbackend + frontend

    The copy route and sheet, Duplicate, and the old copy route's removal.

  7. The MCP toolsbackend

    The new tools, the changed ones, and a briefing rewritten for shared and loose cues.
