Templates: one family, no fixture type

Brief items 8 and 9. Today a template requires an editorFixtureType — that is what resolves the property descriptors the value grid is built from, so “pick a mode” is a required field before you can set a colour.

What that costs today

“Amber Key” authored against a MAC Aura is offered to Auras and refused to the LED bars beside them — the pickers filter on compatibleLookIds, computed from the type. One colour, one template per fixture type.

The swap
1

The family is chosen first and is the template’s identity, not a badge derived afterwards.

2

The editor is family-native — a colour picker, a pan/tilt pad, one level — not a descriptor-driven property list. So no synthetic fixture, and no mode to resolve it against.

3

The stored value is an intent, resolved per fixture when the layer cooks. compatibleLookIds becomes capability-only: does this head have colour at all.

Known cost

Intensity, Position and Colour have cross-type names. Beam does not — gobo and colour-wheel slots are per-type, which is exactly why the mask has four families rather than twenty-two categories. See the Beam & colour artboard for how far this goes and where it stops.

Extract pulls min(r,g,b) into the white/amber emitters — brighter and cleaner, and the sensible default for a wash. Additive drives them alongside RGB. RGB only leaves them at zero, for when a rig is being matched to camera.
