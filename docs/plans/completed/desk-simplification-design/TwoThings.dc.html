Two things, not one thing with a flag

Round 1 called a template “a Look whose rows are deferred” — which is the data model talking, not a design. They do different jobs at different altitudes, so they get different names, different verbs and different pages.

Template
composes values

A named value for one attribute family. “Amber Key”. “Half Up”. “Downstage Centre”.

You point at cells and apply it. It is the desk’s palette: the vocabulary you build everything else out of.

one family no targets no order no timing authored
Look
composes cues

A named state over named fixtures, across any families. “Ghost Entrance”. “Act 1 Opening”.

You add it to a stack as a layer. It is a piece of the show, and it may have been built out of templates.

any families own targets order · mask · amount timing · stomp recorded

One backend table, two front doors

Nothing here needs a second entity server-side. hasDeferredRows plus “exactly one family” already separates them, and a layer already names either by FK. What changes is that the client stops showing one library with two sections and starts showing the two things people actually think in.

The one real backend ask is the single-family constraint on templates, enforced at the write boundary beside validateLookRows — which is also where FU-LOOK-NESTED’s ref: rejection already lives.

Migration is the awkward part

Existing deferred Looks spanning two families are neither thing. They cannot become templates (single-family) and should not silently become Looks (no targets of their own, so they would assert nothing).

Proposal: split them on migration, one template per family, named <name> (colour) / <name> (position), and rewrite each referring layer into one layer per part in the same stack position. Order is preserved because the parts do not overlap by mask. Worth confirming how many in your show would actually split — if it is a handful, doing it by hand beats writing the migration.
