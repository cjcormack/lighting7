Find the show, switch the show, and put it back on its venue

Design session R5 of the venue-visit plan surveyed how the desk is organised around projects: how you reach the list of shows, what a project's own screen shows, which actions hide in a card's ⋮ menu, and whether the sidebar's grouping holds up. It also designs re-attach, which is Detach run in reverse. This page is the readable copy of the plan as it forms. The checked-in markdown is the authority.

What the survey found§1 · main at d35463c, after S2

The code was read on main after venue-visit S2 (f6b37b3, one sidebar state and the install nav), and the running desk was walked with the Commemoration Hall venue and Sleeping Beauty imported.

1 · Reaching the projects listThere's no way to it from the sidebar or the header.
  • The Projects page has no registry entry. You get there from the breadcrumb's root crumb, from ⌘K View All Projects, or by being redirected when no project is current.
  • The sidebar's ProjectSwitcher switches nothing. Its header names the project you're viewing and links to that project's overview.
  • The app bar shows a hard-coded title, "Chris' DMX Controller v7", even though Install Settings already stores a friendly name for the desk.
2 · The project's own screenThe overview is ten shortcut cards, and that's all it is.
  • It shows a name, an active badge, Configure, and cards for Patch, Scripts and FX Library. Seven more cards appear only on the current project.
  • It leaves out the Programmer, Prompt Book, Stage, Templates, Speed Masters, Regions, Rigging and Sync, and has no live state.
  • It has no way to make the project current and none of the card's actions, and it never mentions the venue (its pin, a newer version, History).
  • It ignores the project's kind, so a venue gets Scripts, FX Library, Busk, Looks and Cues cards that the sidebar hides.
3 · The ⋮ menuFive actions live only there, and so does switching shows.
  • Activate Clone Export Detach Delete exist only on a Projects-page card. Import and Add venue exist only as that page's buttons.
  • ⌘K's Go to only opens a project's overview; it never makes the project current. Its Create New Project lands on the list without opening the dialog.
  • A venue's History and Publish appear only on the band across the top of a venue. Extract appears only on the Projects page.
4 · Install settingsAll six tabs are in the nav since S2, but two things are off.
  • The Sync tab is shown to operators, but its nav row is admin-only. The same split shows up again in Project Settings › Sync.
  • Telemetry is a card inside General and has no row of its own.
  • A universe's address is set from a chip on the Patch List, and has no settings home.
  • Account settings (Profile…) live only in the user menu, which is right.
5 · The registry's groupingSix unlabelled groups, divided by rules.
  • setup · program · live · monitor · settings · install render as separators with no headings.
  • Stage sits with Channels under "monitor", even though it's the most-used view after the four live ones.
  • Regions and Rigging are rig authoring, but they're filed under Project Settings. The nav row says Regions where the tab says Stage.
  • Surfaces is the desk's MIDI hardware, but it's a project-settings child.
  • ⌘K lists two rows both labelled Sync, and Project Settings appears twice.
6 · Viewing vs currentViewing another project quietly shrinks the sidebar.
  • Opening a show that isn't current hides every active-only row (Fixtures, Groups, the four live views, Stage, Channels, Surfaces). An "Inactive" badge is the only explanation.
  • On the desk, the TCH venue opened beside Sleeping Beauty shows only Patch List and settings. Its Stage and Programmer are out of reach until the venue is made current, which takes the show off the rig.
  • ChannelsBreadcrumbs is a second, drifted copy of the breadcrumb: its project crumb links to /projects, and its badge is always "active".

Decisionsagreed 2026-10-15 · three rounds

#Navigation plan
D1The app bar names the show on the rig, as a switcher: search, Shows and Venues, each with Open and Make current, then All projects… and New show…. Projects gets a registry row.
D2/projects/:id is the project's home: status first, every action in its ⋮, then the sidebar's sections as cards with counts. A venue's home leads with its version, draft, History, Publish and shows.
D3The sidebar is named sections by job: Run · Rig · Library · Project · Desk. Paths don't change.
D4On a project that isn't on the rig every row stays. A row that needs the rig is muted, with a hollow dot, and opens a page naming the show that is on the rig.
D5The desk's friendly name sits small, before the switcher, and is hidden below 640 px.
#Venue-attach plan
D1Detach records where the show came from (detachedFrom, portable). Matching is three-way where there is an origin: a record the show removed since stays hidden, and one the venue added since comes in. Without an origin, every unmatched venue record comes in, and each can be hidden in the review.
D2A paired patch whose identity differs (key, type, head number, placement count) keeps the show's by default. The venue's is hidden, and the show's stays under a fresh uuid. Take venue's renames the show's references instead.
D3Hall structure (riggings, regions, elements, viewpoints) takes the venue's by default. Groups keep the show's. Each row can be flipped.
D4Both roles may attach, from the project actions and ⌘K, reviewed as Update is. There is an MCP tool, attach_to_venue.

The plans add their own rules. Navigation: one PR per session; a nav row and its page share one predicate (so Sync goes for operators); every project action is defined once; "on the rig" is the server's isCurrent; nothing stored changes. Attach: a detach and re-attach round trip changes nothing; matching is three-way where it can be; the review is the run rolled back; a kept record never shares a uuid with a visible venue record; universes are never hidden.

Does the grouping hold up?§1.5

  • Mostly by kind of page, partly by role. live and monitor are about running the show; setup, program and settings are about building it. Stage is the only view used heavily in both modes, and it's filed under monitor next to Channels.
  • The rig is split across two groups. Patch, Fixtures and Groups are under setup. Regions and Rigging, which are drawn in the same Stage editor, are under settings as Project Settings children.
  • Surfaces is hardware, not show content. Its bindings are per project, but the devices are the desk's. It sits under Project Settings and is hidden on an inactive project.
  • Nothing names a group. With 25 rows, rules between unnamed groups make the sidebar a list to read rather than to scan. In a venue, 9 rows vanish and the separators shift.
  • S4 renames Templates to Palettes (venue-visit D2). This plan uses the new word.

Re-attach: Detach in reversevenue-attach-plan.md

Detach (venue/VenueDetach.kt) writes the effective rig at the show's pin into the show's own rows. It keeps every uuid, re-points the twelve VenueLinks, copies the venue's machine overrides, and flattens the venue's parks into the show's. Then it clears the hides, the overrides and the pin. Today it keeps no record of where the show came from. Uuids are stable across a venue's versions, so a detached show's rows still pair with the same records in any later version.

Pairing, kind by kind

KindFirst byThen byWhen it differs
Universeuuidsubnet:universeThe venue's always: never hidden, never overridden. A different address on this desk is listed as an output change.
PatchuuidkeyAddress, Position, Focus or Media become overrides. If the identity differs (key, type, head number, placement count): keep mine, or take venue's and rename.
Rigging · region · viewpointuuidnameThe venue's by default; keep mine hides the venue's.
Scene elementuuidnameThe VENUE layer only; SET elements stay the show's. The venue's by default.
SeatinguuidnameFixed blocks only. A show's Preset copy never pairs and stays its own.
GroupuuidnameMembers are compared through the patch pairs. Keep mine by default.
Parkuniverse:channelThe same value is inherited, and a different one stays as a re-park. A venue park on a channel the show leaves free becomes a release (the show unparked it), or comes in as an output change (the venue added it since).

The hard cases

CaseWhat the plan does
No origin recordedDetach records it from now on (D1). A show detached earlier, or never on a venue, pairs two-way. Every venue record it lacks comes in, with Hide in this show per row.
Key or name clashThe show keeps a record whose key a different venue record holds. The venue's is hidden if it can be, otherwise this is a blocker (rename yours). Head numbers are checked too; Detach's own check misses them.
Identity differsKeep mine: the venue's is hidden and the show's row takes a fresh uuid, so no uuid is held twice. Take venue's: references in cue, Look and palette rows and bindings are renamed. Scripts are listed, not rewritten.
Universe the venue lacksIt stays the show's own. A paired patch on it becomes an Address override naming the show's universe, which the effective rig holds.
Universe the show lacksIt comes in, since universes can't be hidden. Its patches' address overlaps with the show's are the overlap decisions that Update already makes.
A hide that's refusedVENUE_HIDE_IN_USE: the record comes in, with the reason shown.
Machine overridesThe show's copies of paired records go. A kept record's are re-keyed to its fresh uuid.
Stage sizeThe version's. A difference is listed as drawing only.
Attached behind, on the rigAs a publish does for a running show, it runs against its pin rather than going dark mid-run.

The plan's first test is a round trip. Detaching a show and attaching it back at the same version must leave the effective rig, parks and output unchanged, field for field. The review is the attach run rolled back, as Update's is.
