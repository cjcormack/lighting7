1–2OSC: sender ranges and an address list

Now

A sender is one IP literal, stored canonical, and matched against a packet's source by exact string: a Map<address, sender> lookup for UDP and on every TCP frame. ipLiteral refuses 192.168.0.1/24 as "not an IP address". Nothing in the codebase parses CIDR.

osc/OscService.kt:178–193, 302, 480 · OscReceiver.kt:77–82 · OscTcpListener.kt:67, 93, 150, 160
Change

An address is an IP or a range (a.b.c.d/n, IPv6 /n). A range is stored as its network, so 192.168.0.1/24 is saved and shown as 192.168.0.0/24, with a hint saying so. Matching is one resolver, OscSenderMatcher: an exact address first, then the longest matching prefix. It serves UDP, TCP accept, every frame and the removed-sender sweep. Replies are unaffected, because they already go to the packet's source. The refused list drops any address a new range now covers. A log row carries the packet's source address too, so a message through a range still says which machine sent it.

11Auto numbers from position

Now

An auto number is stored, not computed on read. After any stack write, renumberAutoEntries(stack, before) relabels the auto cues. The exception is an auto cue at the same index as before the write: it keeps its number, and kept numbers act as fixed points (venue-visit plan D11). So a typed or Renumber… number changes the cue before an unmoved auto cue without moving that cue's number. That is how a typed Q30 ends up followed by an auto Q40. A typed number also reads out of order against the autos (1, 4.5, 3, 4, 5) until Fix Order. A stack written before the cue-number migration may carry such gaps from the start.

routes/cueNumbering.kt:149–231, 433–460 · AutoNumberInput.keep
Change

Every auto number is derived from position on every stack write. The keep flag and the before snapshot go. Typed numbers are never touched, and a run between two typed numbers takes the free whole numbers after the first, then decimals only where they run out, as today. What reads out of order is now judged against the typed numbers and the cues before it, never the autos' stored numbers: a typed number is out of order when it is not above the previous typed number that is in order, or, for the first, when the auto cues before it fit neither the whole numbers from 1 below it nor those from 0. So a run with nothing typed before it counts up from 1 where it fits (a lone cue before a typed 1 is still 0), and a typed number too low for the cues before it is flagged with Fix Order rather than squeezing them. A startup step (database step 16) relabels every stack once, logging each change and backing up first if it changes anything. The derivation changes, so sync goes to 54, as it did at v48. A number that reached a desk from an older archive arrived as typed and stays typed.

7Move in dark: instant rows

Now

The China 2-cell blinder (kind = BLINDER) has a parent dimmer, strobe, a built-in program and its speed. Each cell has warm and cold white, plus a Warmth mix. Because the parent has a dimmer, its cells' colour does not count as intensity. So Warmth and white are COLOUR moves, and the program and speed are BEAM moves. Stacks move every family by default, and a head dark for less than delay plus time (1 + 2 s) before a follow reads TOO_QUICK. Nothing asks whether a row has anything to travel.

fixture/dmx/China2CellLedBlinderFixture.kt · fx/MoveInDarkPlanner.kt:231, 303–317 · models/moveInDark.kt:38–48
Change

A row is instant when nothing in the head travels to make it:

  • a mixed colour value, white or amber;
  • a speed on a head with nothing that travels, such as a blinder program's speed;
  • a setting or OTHER that is not a wheel, a media slot or a framing control.

A head whose rows are all instant is set the moment it goes dark: no delay, no move time. So it can never be too quick, and the static plan's live list stops naming it. A head with any travelling row (position, any wheel, including colour wheels declared as colour settings, gobos, prisms, zoom, focus, iris, frost, shutters) moves everything as now, with the stack's delay and time. A speed travels with them on such a head, since on a mover it is the pan/tilt speed. The planner and MoveInDarkService share one predicate, isInstant(row, head).

9A show's name for a venue fixture

Now

A show can take four facets of a venue patch: Address, Position, Focus and Media (PatchFacet). EffectivePatch reads displayName, key, head and type straight from the venue's row. The Patch sheet draws a venue row's name as plain text, and the venue panel says "A show can hide this fixture, not rename or retype it". A display name is checked for uniqueness nowhere, unlike a key.

models/showOverrides.kt:49 · models/patchFacets.kt:229–266 · VenuePatchPanel.tsx:92–105 · PatchSheet.tsx:1185
Change

A fifth facet, NAME: NameFacet(displayName), laid over the version's patch by RigScope.effective, with the same base, drift, Keep mine and Take venue's as the others. The venue diff's identity change on a name becomes drift for a show that holds the name. The key, head and type stay the venue's, so nothing that names the fixture by key moves. The Patch sheet's name cell on a venue row edits it, writing the facet, not VENUE_OWNED. The venue panel gains a Name card. MCP's override_venue_fixtures takes NAME. Detach carries the name into the copy; Attach pairs a renamed patch as a Name override. A name change reloads the live rig, as Address and Media do, and the readers that take a name straight off the venue's row (the patch list's own data first, then the busk rig, group members, cue events, the venue hold and the trigger and command guards) read the show's. Sync goes to 55, because an older desk would refuse the enum value in showOverrides/.

13Selecting text in the Prompt Book while the show plays

Now

Not in production, the lock is !canEdit, and canEdit is "this is the current project". So the lock is not the cause. Two things do disturb a selection while a stack runs:

  • On every change of the live sequence's head (a GO; a follow keeps the head and does not scroll), the page smooth-scrolls to the live cue (jumpToLiveUnlessLinked).
  • Pages outside the render window unmount, which collapses a selection inside them and clears the anchor toolbar through selectionchange.

Neither is confirmed: this needs a browser.

routes/PromptBookPage.tsx:310–323 · promptbook/ScriptViewer.tsx:378–400, 488–528
Change

Reproduce first with Playwright against a running stack with follows, not in production. Then fix what it shows. The expected fix: while a text selection or an anchor toolbar is open, or the pointer is down in the text, the follow scroll waits, and runs once the selection is used or dropped. A page holding the selection stays mounted. If the reproduction shows something else, the session fixes that and records it in the plan.
