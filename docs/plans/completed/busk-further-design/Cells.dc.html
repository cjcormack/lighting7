Multi-head fixtures in a selection

A bar with eight cells is one fixture to the patch and eight to the eye. Every desk answers “which did you mean?” somewhere: Eos on the command line (1 vs 1.3), MagicQ in a programmer-wide element mask, MA in MAtricks, Hog in buddying. lighting7's answer should be on the tile, because the busk view has no command line and a mode is state an operator forgets.

The tile — four states of one Bar L

Bar L8
Not selected. The live bar is per cell — the stage's own colour per element, read the way the mini-stage reads it.
Bar L8
Tap the tile: the whole fixture, as today — {type:'fixture', key:'bar-l'}. Master and every cell, the desk's fan-out.
Bar L4 of 8
Tap a pip, or drag across pips: those cells — four targets, each {type:'fixture', key:'bar-l.pixel-3'}. The tile reads some.
Bar L1–4
Drag from pip 1 to pip 4: a run. On touch the pips are 18×8 at rest and grow to 44px tall under a finger, the marquee's own trick.

The Cells menu, and two steps beside it — a sub-selection over whatever is selected (MAtricks, cut down to what a pad page needs). It rewrites the selection's targets and nothing else: Odd over Bar L and Bar R is eight cell targets; Next walks one cell (or one head, with no multi-head selected) along rig order, which is the chase-by-hand every busking operator does on a bar. Masters only is Eos's Minus Cells — the master's own channels (a bar's global dimmer, its macro) with no cell. Each is a plain selection.set, so it publishes to the desk and the other screen sees it; the chip is the band's, so it exists in Rig focus and in the folded strip.

The wire already has the shape. An element's key is a complete address, never parsed (rowModel.ts's rule), and rowLocateTarget already publishes an element row as {type:'fixture', key: element.key}. So a cell in the selection is not a new target kind; what is missing is on the other side of the press.

Three backend gaps stand between a cell target and a pad press, all already named in lighting7's follow-ups.

1

FU-LOOK-ELEMENT-ROWS — DaoLookRows.elementKey exists but CueComposer.applyLayer skips it, so a Look layer targeted at a cell asserts nothing. Prerequisite PD-TEMPLATE-MULTIHEAD-CELL: parent→element fan-out at cook.

2

templateTargetsFor refuses an element key because /templates/{id}/apply resolves keys against the patch. The resolver needs an element arm: resolve the parent, then the element's own property set.

3

FU-FX-ELEMENT-BUNDLED-COLOUR — elements never receive W/A/UV, so an amber template on Odd cells lands RGB only. Effects already have an element path (elementMode / elementFilter), which is the precedent.

Until those land the tile still draws its pips and the chip still narrows — and a press on cells is refused by name (TARGET_CELLS_UNSUPPORTED), the way a masked press is, rather than silently landing on the whole bar.

Rules the tile states, so nothing else has to

• A group of multi-head fixtures presses whole heads. The group tile is the group target; the desk expands members. Cells are reached by the chip after the group is selected (Odd over Bars = odd cells of both), which keeps the group target opaque and the chip the one place cells are minted.

• Coverage reads cells. A template pad lit against a whole-bar selection reads all; against four cells it reads all too if the applied state names those cells, and some if the desk's applied state names the parent and only some cells are selected. templateLayerPresence folds the parent→cell relation, once, in lookPresence.ts.

• Spread's Over: Cells is where a cell becomes a step, and it is a spread option rather than a selection option because the same eight-cell selection can want either.

• The rig tile chooses how cells show (Rig board): pips on the tile by default, one tile per cell for a bar that is really eight lights, halves for a bar that is really two.
