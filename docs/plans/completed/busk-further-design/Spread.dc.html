Spread: one gesture across a selection

What every desk calls fan: a value at one end, a value at the other, the heads in between filled in by a curve. lighting7 already has the two halves — the sheet kit's FanPopover fans bytes over rows in the programmer, and the FX engine's DistributionStrategy orders heads for an effect. Spread is the busk view's gesture over both, resolved on the desk.

Resolved on the desk: POST /programmer/spread. The client fan (fanMath.ts) lerps bytes over rows it can see; a busk selection is groups, fixtures and cells, and only the desk knows a group's member order, each head's range, which cells a fixture has and what a colour means on a head with amber. So the sheet sends the intent and the desk writes one literal per head into Local, answers what it wrote, and the preview strip draws that answer. Same rule as templates: the client never resolves.

Response and side effects

written[] {target, propertyName, value} in the order used, plus skippedFamilies and skipped[] {target, reason} for a head that lacks the property. Each write is an ordinary programmer entry — so it lands in programmer.entryChanged frames, Record captures it, Blind previews it, and Save as Look… is record-look over the selection, which is how a spread becomes a busk pad.

Live applies on every adjustment through useLiveTempoPush's throttle (50 ms floor, last value always lands), because a fan is judged by eye against the rig. Off, only Apply writes.

Not a template, on purpose. A spread is a result — eight literals — and the library's rule is that a template stores one intent resolved per head. A “spread template” would need a second grammar (two intents plus a curve) and a resolver that knows the selection's order at cook time, which no template does. Saving the result as a Look keeps it recordable and pad-able without widening the template. Revisit only if operators keep re-spreading the same pair.
