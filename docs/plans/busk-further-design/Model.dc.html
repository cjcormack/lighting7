What is stored where, and what is new on the wire

Three homes, as the multi-screen plan drew them: a fact about the project lives on the desk; a fact about this window lives in its tab; a press carries the pair and the desk decides. Nothing here moves a fact between homes.

On the desk, per project backend

-- the rig: two tables, hand-rolled cascades like buskLayout.kt busk_rig_rows (id, project, name, sort_order, uuid) busk_rig_tiles (id, row, sort_order, uuid, group FK | patch FK | (patch FK + element_key), cell_mode WHOLE | PIPS | PER_CELL | HALVES, label?) CHECK busk_rig_tile_exactly_one_ref
GET / PUT /projects/{id}/busk/rignew
whole-document, D10's rule: one PUT per gesture, ids read once at commit, rows and tiles by address. An empty rig is today's band — every group then every fixture — so there is no migration and no first-open generator. busk.rigChanged is one keyed frame; a deleted group or patch takes its tiles off the rig server-side, as a deleted record takes pads off a page.

In this window, per tab client

// lib/buskWindow.ts — deskFollow.ts's model, sessionStorage busk.focus 'split' | 'pads' | 'rig' // default split busk.rigRows number // rows shown in split busk.sheet 'speed' | 'colour' | 'spread' // default speed busk.sheetOpen boolean // default true ≥ md // arrival, latched once per tab like ?page= ?focus=pads ?sheet=none|speed|colour|spread
Why the tab and not the desk. Two screens at one desk want two focuses; a desk fact would pin them together, which is the mistake page follow had to undo. Nothing about focus is a thing the desk's hardware moves.
Why not localStorage. The two desk screens are two windows of one profile — createSyncStore took a storage parameter for exactly this.
Already there, untouched: desk.follow / desk.localSelection, busk.pageFollow / busk.localPage, the window identity and name.
Edit mode stays in the Redux slice (the cue-slot overlay reads it) and forces Split while on.

Where the code goes client

lib/buskRig.ts — the rig document model, sibling of buskLayout.ts: addresses (rrow:{r}, rtile:{r}.{t}), applyDrop, normaliseRig (drops an empty row), toRigRequest, effectiveRig(rig, groups, fixtures) which answers the show-all fallback so the band never has two render paths.
components/busking/RigBand.tsx replaces TargetBand: rows of RigTiles, the handle, the folded strip, the Cells chip; RigTile draws pips and the live bar through fixtureAppearance's colour dispatch. Edit mode joins the app's one DndContext through useDndMonitor, ids prefixed rig- so parseBuskDragId and the slot handler ignore them.
components/busking/SideSheet.tsx hosts three bodies: BuskSpeedRail as it is, ColourSheet (over ColourPickerPopover's content), SpreadSheet. The fold is its own 44px component.
LibraryPalette gains a Rig tab; its rows drag with rig-palette: ids and canLand refuses them everywhere but a rig row.
lib/cellsSubSelection.ts — pure: (targets, fixtures, mode) → targets, pinned by tests against Odd/Even/halves/Next/Prev/Masters.
lib/handTargets.ts gains a rig-row place for a group or fixture held in the hand (a rig tile is a reference like a pad).
1The rig
Backend tables + PUT + frame; buskRig.ts; RigBand in play; the Rig palette tab in edit. Cells drawn as pips (read-only feedback), no cell selection yet. Ships the show-all fallback first, so the band is bit-identical until someone builds a rig.
2Focus and the fold
Client only: buskWindow.ts, the segmented control, the handle, the folded strips, the sheet fold and tabs (Speed only), ?focus= ?sheet=, the ⌘K arms, the Screens sheet's per-view options and the widened link. windows.viewOptions is a small backend add.
3Colour
Client only: ColourSheet over programmer.setColour, Recent from the recents row, Pick from the stage source, Save as template through from-programmer. Below md, reachable from the narrow target sheet.
4Spread
POST /programmer/spread and the resolver's curve/order/parts; SpreadSheet with the preview strip fed from the response; Spread… on the band; Save as Look. The Colour tab's second-colour switch hands over to it.
5Cells
The element arm on every press route and in coverage; pips become tappable; the Cells chip; Over: Cells on Spread; MIDI Next/Prev. The one session that is mostly backend, and the one to schedule against the rig checks.

Order matters in one place: 5 depends on 1 (pips) and 4 (Over); 2, 3 and 4 are independent of each other and of 1. If only one thing ships, ship 2 — it is client-only, it is what the two-screen desk is asking for, and it costs nothing on the wire.
