Three surfaces already exist for this — the user menu (where per-viewer things live), the app header's panel toggles, and ⌘K. Nothing new goes in the header row: it is nine controls wide and already off the edge of a phone. 4 · Escwhy the desk should run installed
Esc, and what it does now

A browser leaves element full screen on Esc, and Esc is also the sheet's clear-selection key and every dialog's close. In a plain tab the browser takes it first and the app never sees it, which is why the installed route is the recommendation for the desk. Chrome's Keyboard Lock (navigator.keyboard.lock(['Escape'])) keeps Esc in a fullscreen window and is worth a feature-detected call on the Full screen path; there is no equivalent in Safari. In full screen the app draws a small exit glyph in the user menu only — never a floating button on a live view.

5 · Four ways out of the browser chromeand which one each surface should use
In the app

A Full screen item in the user menu and in ⌘K, on document.documentElement.requestFullscreen(). Needs a gesture, so it cannot happen on load — but it can be remembered: a window that was full screen last time shows a one-tap Return to full screen banner on reload.

Installed (the desk)

Install the app once per browser profile: the manifest says display: fullscreen (with standalone as the fallback), and every launch is chromeless with no gesture and no Esc trap. This is what the two desk screens should run. The Windows install already ships a browser; add a --app= shortcut per screen.

Kiosk (unattended)

Chrome --kiosk or the OS kiosk mode for a screen nobody should be able to leave — a front-of-house tablet. Nothing to build; a note in the docs.

iPad

Safari on iPadOS honours requestFullscreen on the document, so the same item works. Add to Home Screen is the durable route: standalone hides the address bar and keeps the session cookie.
